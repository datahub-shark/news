摘要

RM Studio PC 是面向 RoboMaster 整车电控的综合调参与运行观测工具。它把参数修改、传感器数值查看、并发任务观测、线程执行时间分析、实时数据曲线和协议诊断集中到同一个上位机工作台中。自瞄、云台、底盘和发射机构都可以使用同一套数据采集与观测机制。

本文以原文档为基础，采用白皮书、技术报告和使用说明书的组织方式，重点说明“下位机采集并发布数据，上位机接收、解析、呈现和辅助调参”的完整链路。自瞄只作为一个典型应用场景，用来说明视觉延迟、云台转角/转速、控制误差和任务执行时间如何被观测。


1. 项目背景：为什么整车电控需要统一观测工具

1.1 RM Studio PC 的总体定位

整车电控开发中，工程师往往需要同时查看 IMU、编码器、电机、底盘、云台、视觉、功率和通信状态。如果这些数据分别通过临时串口打印、独立脚本和不同调试工具输出，就很难在同一时间线上判断问题。RM Studio PC 的设计目的，是把这些调参和观测对象统一接入，通过设备端目录和协议动态发现数据，再在 PC 端进行集中展示。

它主要服务于以下工作：

  • 修改控制器、限幅、零位、方向和输入等参数；
  • 查看 IMU、编码器、电机反馈、功率和通信等传感器或状态数据；
  • 观察并发任务、线程执行时间、周期抖动和 CPU/栈使用情况；
  • 分析视觉数据到 MCU 控制链路的延迟；
  • 查看云台转角、转速、目标值、误差、输出和电机电流；
  • 通过原始协议帧确认下位机是否正确发送和响应。

1.2 自瞄只是整车观测中的一个典型场景

以步兵或英雄机器人为例，自瞄链路可以抽象为：

```

相机图像

 -> 目标检测

 -> 装甲板/目标跟踪

 -> 相机坐标系下的位置与姿态解算

 -> 目标筛选与预测

 -> 云台目标角度

 -> 角度环 / 速度环

 -> 电机输出

 -> 云台运动

 -> 下一帧图像

```

视觉端通常负责从图像中得到目标信息，控制端负责把目标信息转换为云台能够执行的角度和速度指令。RM Studio PC 不参与视觉识别本身，而是观测视觉数据进入下位机后的结果、时间戳和控制反馈。最终的命中效果取决于整个闭环，而不是某一个模块单独的识别准确率。

例如，视觉输出已经稳定，但 yaw 正方向配置错误，云台仍会向相反方向运动；PID 参数正确，但视觉消息延迟过大，云台会始终追着目标的历史位置运动；控制周期正常，但目标角度没有经过限幅，云台可能在边界附近产生突变。因此调试自瞄时，必须同时观察输入、目标、测量值、误差、控制输出和系统状态。

1.3 下位机到上位机的数据链路

RM Studio PC 的数据链路可以概括为：

传感器 / 控制任务 / 视觉通信输入
             -> 下位机采集与数据注册
             -> TU/v2 参数协议、RM/v1 监控协议
             -> PC 端 StudioClient 接收与解析
             -> 上位机曲线、状态卡片、Trace 和诊断面板

下位机负责采集数据、维护参数、执行控制任务、记录时间戳并按照协议发送；上位机负责建立会话、订阅需要的变量、接收异步样本、解析数据并呈现给开发者。上位机看到的每一项数据，都应能追溯到下位机端的变量定义或任务事件，而不是由 PC 端凭空推算。

1.4 传统调试方式的不足

只依靠重新烧录、串口打印或肉眼观察，通常会遇到以下问题：

  • 参数修改需要反复编译和烧录，难以快速比较多组参数；
  • 日志只打印离散事件，无法连续观察目标角度和实际角度的关系；
  • 控制环、视觉状态和电机输出分散在不同日志中，难以对齐时间；
  • 多个工具同时读取串口，可能造成数据竞争和回包丢失；
  • 参数写入后，难以区分“本次会话生效”和“已经保存到 EEPROM”；
  • 偶发卡顿发生时，普通日志往往无法保留异常前后的执行时间信息。

RM Studio PC 的目标，就是把这些调试工作放到同一个工作台中完成。

1.5 RM Studio PC 在整车系统中的位置

RM Studio PC 位于整车电控系统的“调试与验证层”，自瞄、底盘、云台和发射机构都是它的观测对象：

```

视觉程序 / MCU 控制程序 / 云台驱动

             ^

             | TU/v2 参数协议、RM/v1 监控协议

             v

         RM Studio PC

```

它可以帮助开发者回答：

  • 视觉是否在线，系统当前处于什么模式；
  • 视觉目标角度是否正确到达 MCU；
  • 目标角度和云台实际角度之间的误差是否收敛；
  • 角度环、速度环的输出是否饱和或抖动；
  • 云台任务是否超时、周期是否异常；
  • 当前修改是临时参数还是已保存参数；
  • 串口没有回包时，问题出在物理链路还是协议解析。

它不替代下位机的实时控制和算法执行，也不直接完成：

  • 从相机画面中检测装甲板；
  • 训练或运行 YOLO 等目标检测网络；
  • 进行 PnP、卡尔曼滤波或目标轨迹预测；
  • 替代 MCU 上的 PID、限幅、状态机和电机控制；
  • 在没有 MCU 协议支持的情况下读取任意串口变量。

这个边界是理解 RM Studio PC 的前提：下位机负责实时执行和发布数据，上位机负责配置、观测、记录和诊断。


2. 软件界面与整车电控观测功能总览

2.1 工作台总览

软件启动后可以看到设备信息、会话状态、车辆状态、参数数量、未保存改动和 EEPROM generation。界面把参数生命周期明确分成三层：

```

Module Default  ->  EEPROM Saved  ->  Session Current

代码默认值          已持久化配置        当前会话临时值

```

  • Module Default 是固件或模拟器定义的默认值；
  • EEPROM Saved 是已经写入 MCU 持久化存储的值；
  • Session Current 是本次连接中实际参与控制的当前值。

图 1：RM Studio Demo 总览

进入真实调试前，先确认设备名称、会话状态、车辆状态和参数数量。尤其是云台调试，不要在没有确认车辆处于安全状态时直接修改限位、输出上限或方向参数。

2.2 参数工作台：整车参数如何被组织

参数页不把参数表写死在 PC 端，而是由 MCU 通过 Parameter Registry 动态返回。这样同一套上位机可以适配不同机器人项目，参数的类型、单位、范围、步长和写入策略也由设备端提供。

图 2：参数工作台

这里的类别不是 PC 端预先写死的固定菜单，而是 XuanShu-Tune 下位机 Demo 当前注册出来的结果。项目开发者可以在实际模块变量旁边注册自己需要调节的参数；因此，底盘、发射、功率、舵轮、悬挂或其他模块都可以使用同一套机制扩展，PC 不需要为每个机器人重新修改界面。

2.2.1 下位机如何定义“可以调哪些参数”

在 RM_Studio_MCU/include/tune/param.hpp 中，参数描述符包含 id、component、name、unit、type、value_ptr、factory、min_value、max_value、step、max_step、policy 和可选的 apply 回调。也就是说，参数的名字、数据类型、单位、范围、步长、默认值、是否持久化以及什么车辆状态下允许写入，都是由下位机工程决定的。

include/tune/bind.hpp 提供 TUNE_BIND_F32、TUNE_BIND_F32_UNIT、TUNE_BIND_F32_SAFE、TUNE_BIND_I32、TUNE_BIND_U32、TUNE_BIND_BOOL 以及带 Apply 回调的变体。绑定宏把描述符放入 rm_tune_params linker section，启动时由 Registry::FromLinker() 自动收集。因此不需要再维护一个集中式 xxx_tune.cpp 参数清单，参数可以直接放在所属模块的变量定义附近。

例如 RM-Test/programs/XuanShu-Tune/gimbal/src/gimbal_data.cpp 中，云台工程自行注册了几何参数、输入参数、IMU/视觉映射参数，以及 pitch/yaw 的角度环和速度环 PID 参数：

TUNE_BIND_F32_SAFE_APPLY(
    "gimbal.pitch_angle", "kp", cfg::gPitchAnglePid.kp, "",
    0.0f, 5000.0f, 0.1f, 200.0f,
    tune::WritePolicy::Live, GimbalTunePidChanged, nullptr)

这个示例表示：参数属于 gimbal.pitch_angle 组件，名称为 kp，绑定到下位机实际变量 gPitchAnglePid.kp，可写范围为 0 到 5000，推荐步长为 0.1，单次最大变化为 200，并在写入后通知控制任务重新应用 PID。若另一个底盘工程注册 chassis.velocity.kp，PC 端会在收到新的 catalog 后自动出现该参数；界面不需要预先知道它的存在。

下位机还会根据 WritePolicy 和当前 VehicleState 做最终检查。Live、SafeOnly、KillOnly 和 ReadOnly 只是参数的安全策略，不是 PC 端可以绕过的权限。对于涉及电机方向、机械限位和几何零位的修改，Demo 使用 KillOnly 或 SafeOnly；对于 PID 数值，部分参数允许 Live 写入，但 Apply 回调只设置 pending 标志，由拥有控制对象的 GimbalTask 在自己的执行上下文中调用 ReInitPID，避免 Tune 后台任务直接操作电机。

参数的生命周期可以概括为：

模块变量与 TUNE_BIND 注册
  -> MCU Registry 自动收集
  -> TU/v2 CATALOG_PAGE 发布元数据
  -> PC StudioClient 解析 catalog 并生成参数界面
  -> READ/WRITE 修改 Session Current
  -> SAVE 写入 MCU 的 A/B Flash 或 EEPROM 存储
  -> 重新连接检查 Saved、generation 和 dirty 状态
参数类别典型参数调试用途
geometrypitch_offset_rad、yaw_offset_rad、轴限位、反向标志处理机械零位、安装偏差和方向问题
input摇杆速率、鼠标速率、通道符号区分手动控制输入与自动控制输入
pitch_anglekp、ki、kd、max_out调整俯仰角度环的响应和输出限制
pitch_speedkp、ki、kd、max_out调整俯仰速度环的跟随和阻尼
yaw_anglekp、ki、kd、max_out调整水平角度环
yaw_speedkp、ki、kd、max_out调整水平速度环
visionpitch_sign、yaw_sign、坐标模式对齐视觉坐标和云台控制坐标
imupitch_sign、yaw_sign对齐 IMU 姿态方向

这些参数说明了 RM Studio PC 的作用：它可以调节下位机已经实现的控制器和整车模块参数，但不替代下位机执行控制算法。参数是否允许写入由设备端策略决定：

  • LIVE：允许在运行过程中修改，但仍受故障状态限制；
  • SAFE_ONLY：只允许在 KILL 或 SAFE 状态修改；
  • KILL_ONLY：只允许在 KILL 状态修改；
  • READ_ONLY：只读参数。

PC 端显示的 Policy 只是提示，最终拒绝或接受写入的是 MCU。这样可以避免上位机误操作绕过车辆安全状态。

2.4 PC Trigger Recorder：抓住偶发异常

某些问题只在特定时刻出现，例如目标快速切换、视觉短暂离线、云台接近限位或发射机构动作时的瞬态冲击。PC Trigger Recorder 记录的是 PC 已接收到的数据，并保留触发点前后的窗口，适合分析：

  • 视觉在线状态变化；
  • 目标角度突变；
  • 误差突然增大；
  • 输出饱和；
  • 采样丢帧或通信拥塞。

它不会修改 MCU 状态机，也不会代替 MCU 保存完整的实时历史数据。

2.5 运行分析与 Execution Trace

运行页按需获取 RTOS Task Snapshot，并通过 Trace 观察并发任务和执行区间。它可以帮助判断整车问题究竟是数据问题、控制问题还是实时性问题：

  • 视觉消息是否长时间没有更新；
  • 云台控制任务是否周期异常；
  • 某个任务是否占用过多 CPU；
  • 栈剩余空间是否过低；
  • 某个执行 Scope 是否出现长尾延迟。

3. 整车数据与自瞄场景的工程化分析方法

3.1 先区分“目标错误”和“控制错误”

当整车表现异常或准星没有对准目标时，不要立即修改 PID。应先同时观察下位机发布的输入、传感器和任务数据：

  1. target 本身跳动，说明视觉、坐标变换、预测或消息时序可能有问题；
  2. target 稳定而 angle 不跟随，优先检查控制器、方向符号、输出限幅和机械负载；
  3. target 与 angle 的误差稳定但不归零，可能存在机械零位、安装偏差或角度偏置；
  4. angle 能跟随但电流很大，优先检查阻尼、摩擦、负载和速度环参数；
  5. 曲线整体正确但开火偏移，才进一步检查发射延迟、弹道补偿和枪管/云台标定。

3.2 坐标系、符号与角度偏置

在云台和视觉场景中最容易被忽略的是坐标系、时间戳和延迟。至少要明确：

  • 相机坐标系的左右、上下和前方定义；
  • IMU 输出的 yaw/pitch 正方向；
  • 云台电机编码器的正方向；
  • vision.pitch_sign、vision.yaw_sign 是否与控制器一致；
  • 机械零位与软件零位之间的偏置；
  • 使用绝对世界角，还是使用相对云台角。

例如，当目标位于图像右侧时，如果视觉端输出正 yaw，而云台向左运动，问题首先不是 PID，而是坐标符号或通道方向。此时应在低功率、安全状态下验证 yaw_sign 和 yaw_channel_sign，不要通过增大 PID 参数掩盖方向错误。

3.3 串级 PID 的观察顺序

本项目示例将 pitch 和 yaw 都拆成角度环与速度环。调试时建议按照以下顺序：

```

机械零位与方向

 -> 速度环

 -> 角度环

 -> 目标角度输入

 -> 视觉在线与延迟

 -> 预测和发射联动

```

速度环没有稳定时，角度环会把问题放大；角度环没有稳定时，视觉目标输入会让人误以为“识别抖动”。建议每次只修改一个因素，记录修改前后的 target、angle、error、omega 和 output 曲线。

3.4 通过曲线识别常见问题

曲线表现优先怀疑的原因
target 与 angle 同步但整体偏移零位偏置、安装偏差、offset_rad
target 稳定，angle 高频振荡角度环或速度环增益过大、采样噪声、机械共振
误差长期存在且输出已饱和电机能力不足、限幅过小、负载过大、方向配置错误
target 每帧跳变视觉检测/跟踪不稳定、目标选择变化、消息不同步
角度跟随滞后但曲线平滑控制增益偏低、输出限幅、视觉或通信延迟
视觉在线频繁变化视觉进程、通信链路、心跳或超时配置问题
曲线偶尔断开订阅频率过高、带宽预算不足、MCU 任务阻塞

5. 连接真实 MCU 的操作流程

第一步：确认 MCU 端协议和变量

RM Studio PC 不是通用串口助手。MCU 端应提供参数目录、参数读写、会话 heartbeat、监控变量目录、变量订阅与异步样本，并按需要提供 Trace 和 RTOS Snapshot。

要调试自瞄，还应确认 MCU 实际发布的变量与界面含义一致，例如 gimbal.yaw.target 是否确实是视觉或火控输出的目标角，而不是手动输入目标。

第二步：连接链路

  1. 选择 UART、USB-CDC 或 DEMO；
  2. 刷新端口并选择目标 COM 口；
  3. 设置与 MCU 一致的波特率，示例为 921600；
  4. 点击“连接设备”；
  5. 等待设备名、heartbeat、参数数量和会话状态出现。

同一物理串口只能由一个接收所有者持续读取。连接 RM Studio PC 后，不要再让其他串口工具同时读取同一个 COM 口。

第三步：确认安全状态

云台和发射机构调试前，确认机器人处于 KILL 或 SAFE，电机输出和发射机构有物理保护，云台运动范围内没有人员和障碍物，参数修改使用小步长，并且不绕过 MCU 的状态保护。

第四步：读取参数并进行小步调试

  1. 在参数页搜索目标参数；
  2. 对照 Default、Saved、Current；
  3. 查看单位、范围、步长和 Policy；
  4. 先修改 Session Current；
  5. 通过 Watch 观察效果；
  6. 验证通过后再保存到 EEPROM；
  7. 结果不正确时，优先 Discard 当前会话改动。

第五步：订阅最小变量集

```

  1. vision.online / system.mode
  2. yaw.target / yaw.angle
  3. pitch.target / pitch.angle
  4. yaw/pitch error / omega
  5. output / motor current
  6. Trace 与运行任务

    ```

每一步先确认上一层数据合理，再增加下一层变量。这样能够把传感器、视觉、控制、驱动、并发和实时性问题分开。


6. 协议与软件架构白皮书

6.1 组件关系

```

Web UI

 -> QWebChannel

 -> TuneBackend

 -> 请求队列 / Acquisition Worker

 -> StudioClient

 -> Transport

 -> MCU

```

qt_app.py 负责创建 QWebEngineView 和 QWebChannel；qt_backend.py 负责连接、会话恢复、采集 worker、导入导出以及 Qt 信号；client.py 负责协议请求和接收；protocol.py 负责帧编码、解码、CRC16 和数据结构；transports.py 提供串口抽象；mock_transport.py 提供无硬件模拟。

6.2 单一 RX Owner

同一个物理串口只有 StudioClient 的接收线程负责读取字节流。收到数据后，分别尝试解析 TU/v2 和 RM/v1 帧：

```

串口字节流

 -> TU/v2 帧解析 -> 参数请求、状态、会话

 -> RM/v1 帧解析 -> Watch 样本、Trace、任务快照

```

同步请求通过 command + sequence 匹配回包；异步 SAMPLE 和 TRACE_EVENT 进入独立队列。这样可以避免参数请求、heartbeat、监控样本和 Trace 被不同线程同时读取而互相抢包。

6.3 TU/v2 参数协议

TU/v2 负责 HELLO、HEARTBEAT、GET_INFO、CATALOG_PAGE、READ_PARAM、WRITE_PARAM、SAVE、DISCARD、RESET_FACTORY 和 GET_STATUS。

每个参数目录项包含 ID、类型、组件、名称、单位、最小值、最大值、步长、最大单步变化、指纹和默认值。写入失败时，设备可以返回 READ_ONLY、RANGE、STATE_DENIED、STEP_TOO_LARGE、VALIDATION 等明确状态。

6.4 RM/v1 监控协议

RM/v1 负责 SUBSCRIBE、UNSUBSCRIBE、CLEAR_SUBSCRIPTIONS、GET_STATS、TRACE_ENABLE、TRACE_CLEAR、RUNTIME_TASKS、TRACE_CATALOG_PAGE、SAMPLE 和 TRACE_EVENT。

监控目录提供变量类型、推荐频率、最大频率、分组、名称和单位。订阅频率不是越高越好，应结合变量数量、串口带宽、MCU 负载和前端显示需求确定。

6.5 帧格式与 CRC

两种协议都采用带 magic、版本、命令、序号、payload 长度和 CRC16 的帧结构：

```

magic | version | command | sequence | payload_length | payload | CRC16

```

CRC 校验用于判断帧在传输过程中是否损坏。协议 Probe 可以打印原始帧，用来把“没有设备响应”“响应被其他程序读走”“CRC 错误”和“PC 解析错误”区分开。

6.6 会话、心跳与回滚

Tune 和 Monitor 都需要建立会话并持续 heartbeat。会话超时后：

  • Tune 的未保存 Session 改动回退到 Saved；
  • Monitor 会清理订阅和 Trace 状态；
  • PC 端应把断连、超时和回滚状态展示出来。

因此，Current 变成 Saved 不是因为界面显示成功，而是必须经过 MCU 的保存响应，并由 generation、slot、dirty 等状态确认。

6.7 安全中心：为什么参数权限不能只由 PC 决定

安全页面不是装饰性的状态面板，而是调参操作的安全边界说明。它同时呈现 Vehicle Supervisor、Session Lease、Heartbeat、车辆状态、权限策略和违规计数，帮助操作者判断当前是否允许写入，以及当前连接是否仍然有效。

安全控制分为三层：

  1. Vehicle Supervisor：由 MCU 根据车辆状态决定当前处于 KILL、SAFE、ARMED、RUNNING 或 FAULT 等状态；
  2. Session Lease：Tune 和 Monitor 会话通过 HELLO 建立，并依靠 heartbeat 续租，超时后自动清理或回滚；
  3. Parameter Policy：每个参数拥有 Live、SafeOnly、KillOnly 或 ReadOnly 策略，MCU 在真正写入前再次验证。

因此，PC 端把按钮置灰只是减少误操作，不能替代 MCU 的拒绝逻辑。即使用户构造写入帧，MCU 仍应根据车辆状态、范围、步长、最大单步变化和自定义 Validate 回调拒绝不安全请求。XuanShu-Tune 中的几何零位、方向和限位参数使用更严格的 Kill/Safe 策略；PID 的一部分数值允许 Live 修改，但 Apply 回调只通知 GimbalTask 在控制任务上下文中应用。

6.8 存储中心：Default、Saved、Current 与恢复

存储页面用于解释参数从哪里来、当前改了什么、保存到哪里、断开后会发生什么。三层值的含义不同：

层级来源作用
Module Default / Factory固件代码中的 factory value新设备初始化和恢复出厂的基准
EEPROM SavedMCU A/B 持久化存储重新上电后恢复的已确认配置
Session Current当前 Tune 会话本次连接临时生效、可观察和可撤销的值

MCU 配套库不把 Flash 驱动写死在库中，而是通过 tune::StorageBackend 接入用户现有的 Flash/EEPROM API。正式实现使用 A/B 双 Slot：每个 Slot 保存 generation、schema/factory 信息、参数快照和 CRC16；新配置写入备用 Slot，回读校验通过后再切换 active Slot。这样一次写入失败或掉电时，旧 Slot 仍可作为有效配置。

常见操作的语义如下：

  • Save EEPROM：把 Session Current 提交到 MCU 存储，成功后更新 generation、active slot 和 Saved 值；
  • Discard Session：放弃当前未保存改动，恢复到 EEPROM Saved；
  • Reset Factory：按 MCU 的 factory value 恢复默认配置，属于高风险操作，需要明确确认；
  • Export JSON / C Header：把当前参数目录或配置导出，用于实验记录、代码固化和跨设备比较；
  • Import JSON：把已记录的参数集导入当前 Session，仍需经过 MCU 的范围、策略和状态检查，不能绕过安全控制。

离线状态下，PC 端仍可以运行 Demo/MockTransport，查看参数工作台、存储层次、Watch、Trace 和日志功能；但离线数据只是模拟数据，不能证明真实硬件已经调通。真实设备断开时，PC 应显示 OFFLINE，并停止把当前缓存误认为 MCU 的实时值。Session heartbeat 超时后，MCU 负责撤销未保存会话改动；重新连接时，PC 应重新读取 catalog、status 和 Saved 值，而不是盲目沿用上一次内存状态。

6.9 日志与协议诊断：把“没有反应”拆成可验证的问题

日志页面记录上位机侧的操作结果和通信证据，包括连接、heartbeat、参数读写、保存、回滚、Watch 订阅、Trace、超时和错误码。日志过滤用于从长时间调试记录中快速定位 PARAM、SAFETY、STORAGE、ERROR 等类别；清空日志只清理 PC 当前显示缓存，不代表删除 MCU Flash 配置。

Raw Capture 用于记录原始 TX/RX 字节，适合判断 PC 是否真的发出了 TU/RM 请求、MCU 是否返回完整帧、长度和 CRC 是否正确，以及问题发生在物理链路、协议帧、客户端解析还是界面渲染。手动探测功能可以分别发送 TU HELLO、RM HELLO 或指定 Raw Hex 帧。使用时必须先关闭其他串口工具，并保持单一 RX Owner 原则。

6.10 RM Studio 的完整开源组成

RM Studio 不是只有一个 PC 界面，而是由协议兼容的 PC 上位机、MCU 公共配套库和测试/示例工程共同组成：

rm-studio-pc -> Qt/JavaScript 工作台、StudioClient、TU/v2、RM/v1、MockTransport
rm-studio-mcu -> Tune Registry、Watch Registry、Trace、Runtime、ConfigStore、协议服务
RM-Test / XuanShu-Tune -> 真实工程接入示例、参数注册、Watch 发布、Flash A/B 适配和验证

rm-studio-mcu 是 C++17 独立库，故意不拥有 STM32 HAL、UART/USB 驱动、FreeRTOS、Flash 驱动或 DJI Board 专用层。用户工程通过 Transport、Clock、StorageBackend、RuntimeHooks 和 VehicleState 回调接入现有底层。MCU 端只提供业务协议和注册机制，不重新制造一套 BSP。

最小接入步骤是：将库加入 CMake，使用 TUNE_BIND_* 注册参数，使用 RM_WATCH_* 注册观测量，再把现有 UART/USB、时钟、Flash 和车辆状态映射到公共接口，最后在低优先级调试任务中调用 StudioRuntime::ProcessOneSlice()。不同机器人只需替换下位机注册内容，PC 端仍可复用。

当前 MCU 独立库已经包含 Host 侧 CRC、Registry、Config、Protocol、Monitor 等测试；XuanShu-Tune 验证了 Type-C 板、UART6 921600、云台参数、视觉/IMU Watch、RTOS Runtime 和 A/B 存储的整合方式。真实 UART/USB、目标板 Flash sector 和 ARM 交叉编译仍需在目标硬件上继续验证，文档不把 Host 测试冒充成实机结果。


7. 技术选型与系统定型

7.1 选型目标

RM Studio PC 的技术选型不是单纯追求界面效果，而是围绕整车电控调试的四个约束确定：第一，参数和监控变量必须由下位机项目自定义；第二，实时数据不能因为前端刷新或日志显示而阻塞控制链路；第三，Tune 参数请求、Watch 样本、Trace 事件和运行时任务数据需要在同一条物理链路上并行工作；第四，界面必须适合长时间观察、快速筛选和反复实验。

在交互层面，项目参考了 BF 地面站常见的工作方式：设备连接后持续刷新状态，用户选择数据源后只更新相关区域，实时值与历史曲线分层显示，页面结构变化和数据数值变化采用不同刷新策略。参考的重点是“实时数据驱动界面”和“前后端分工”，不是照搬 BF 的项目内容或协议。

7.2 前端方案：Qt WebEngine 与 JavaScript 工作台

PC 端采用 PyQt5 创建桌面窗口，通过 QWebEngineView 承载 HTML/CSS/JavaScript 界面，通过 QWebChannel 建立 Python 后端与 JavaScript 前端之间的对象通信。这样选择的原因是：Python 便于实现串口、协议解析、日志和测试工具，Web 技术便于组织复杂的参数表、曲线、筛选器和多页面工作台，同时保留桌面应用的串口和文件访问能力。

前端主要负责四类任务：

  1. 展示设备状态、Session、车辆安全状态、参数 Default/Saved/Current 和 Watch 订阅状态；
  2. 接收后端推送的状态、参数、Watch 样本、Trace 和 Raw TX/RX 事件；
  3. 管理用户交互，例如选择组件、搜索参数、修改采样频率、暂停曲线和设置触发条件；
  4. 执行轻量级显示计算，例如曲线窗口裁剪、坐标缩放、最新值卡片刷新和前端绘制调度。

前端不直接读取串口，也不在浏览器脚本中实现 MCU 协议。所有设备访问都通过后端对象完成，避免多个页面或多个 JavaScript 回调同时抢占物理串口。

7.3 后端方案：协议客户端、状态桥接与异步采集

qt_backend.py 是 Qt 前后端之间的状态桥接层，client.py 是协议和物理传输的核心。后端负责建立 Tune Session 和 Monitor Session、发送 HELLO/HEARTBEAT、分页读取参数目录和 Watch 目录、执行参数读写与保存、订阅监控变量、接收异步样本、读取 RTOS Snapshot、控制 Trace，以及把结果转换为前端可消费的状态对象。

后端内部采用“控制平面”和“数据平面”分离的设计：

平面典型内容主要特点
控制平面HELLO、HEARTBEAT、CATALOG_PAGE、READ/WRITE、SAVE、SUBSCRIBE、GET_STATS请求-响应、需要序号匹配、需要超时和错误反馈
数据平面Watch SAMPLE、TRACE_EVENT、Raw RX、实时曲线样本异步到达、允许批量处理、不能被同步请求读走

StudioClient 内部只有 _rx_worker 一个线程调用 transport.read()。它持续读取字节，依据 TU 或 RM magic、版本、命令和序号解析完整帧；同步回包进入 pending 队列，Watch SAMPLE 和 TRACE_EVENT 进入异步队列。这样 Tune 的参数写入、Monitor 的订阅和实时样本可以共用一条 UART，而不会因为多个线程同时读串口造成字节被错误线程消费。

7.4 实时刷新机制：采集频率不等于绘制频率

实时刷新不能简单理解为“收到一帧数据就重绘一次页面”。下位机采样频率、串口传输频率、后端状态推送频率和浏览器绘制频率是四个不同概念：

MCU Watch 采样
  -> RM/v1 SAMPLE 异步帧
  -> StudioClient 解码
  -> 后端保存最新值与有限历史
  -> 前端按显示节奏批量消费
  -> Latest 卡片 / Scope 曲线 / Trigger Recorder

在当前前端实现中，最新值区域目标刷新周期约为 100 ms，适合显示当前状态；Scope 曲线使用 requestAnimationFrame，目标绘制间隔约为 33 ms，并根据最近绘制耗时自动调整到 40 ms 或 50 ms，防止窗口尺寸较大、曲线较多时拖垮 UI。采样数据仍然可以按 MCU 允许的频率接收，但显示层不会机械地为每个样本创建一次 DOM。

这套机制解决了两个常见问题：一是数据频率很高时页面闪烁、卡顿和 CPU 占用升高；二是数据频率较低时页面重复刷新，造成“看起来在动”但没有新增信息。实时值卡片强调低延迟的当前状态，Scope 强调连续趋势，Trigger Recorder 则保留触发点前后的历史窗口，三者不使用同一种刷新策略。

7.5 前端数据结构与渲染稳定性

实时变量在前端分为 watchCatalog、watchSubscriptions、monitorLatest 和 monitorSeries：

  • watchCatalog 保存下位机动态发布的变量元数据；
  • watchSubscriptions 保存用户当前选择的变量和采样频率；
  • monitorLatest 保存每个变量最近一次有效值，用于最新值卡片；
  • monitorSeries 保存曲线窗口内的时间戳和值，用于 Scope 和触发记录。

Watch 目录不会因为每次 heartbeat 都重新生成 DOM。前端会计算目录、搜索条件、订阅状态和加载状态的签名，只有结构确实发生变化时才重建变量列表。这一点对 Windows/QWebEngine 下拉菜单和输入控件尤其重要，可以避免用户正在选择采样频率时界面被后台刷新打断。参数编辑器也采用编辑锁：用户进入设置状态后，后台读值不会覆盖正在输入的草稿，只有点击应用或取消后才恢复同步。

7.6 为什么最终采用这套方案

综合需求和验证结果，项目最终确定以下技术方向：

  1. 设备端动态 Registry：参数和 Watch 由下位机工程定义，上位机只消费目录元数据；
  2. TU/v2 与 RM/v1 双协议：参数配置和实时监控分开建模，减少互相影响；
  3. 单一 RX Owner：所有串口接收由 StudioClient 统一处理，避免并发读串口；
  4. Qt WebEngine + QWebChannel：利用 Python 的硬件与协议能力，以及 Web 前端的界面组织能力；
  5. 异步样本队列 + 前端节流渲染：保证实时数据连续到达，同时控制页面绘制成本；
  6. 目录签名和编辑锁：避免后台刷新破坏用户操作状态；
  7. Watch 订阅和带宽预算：用户只选择需要的数据，并显示 active count、estimated bandwidth、max bandwidth 和 dropped 统计；
  8. 运行态按需采集：Runtime Snapshot、Trace 和 Scope 只有在对应页面或功能启用时增加采集负担。

这些决策共同构成 RM Studio PC 的“前端实时工作台 + 后端协议服务 + 下位机数据发布”架构。它既能支持 XuanShu-Tune 的云台参数调试，也能扩展到整车其他模块。

7.7 从需求到定型的工程流程

技术方案的形成按照“需求提取、接口验证、Demo 联调、性能观察、风险收敛、版本固化”的顺序进行：

  1. 从整车调试任务中提取参数调节、传感器查看、任务并发观测、Trace、存储和协议诊断需求；
  2. 在 MCU 端先验证参数描述符、Watch 描述符、车辆状态和存储后端，再设计 PC 端展示；
  3. 以 XuanShu-Tune 验证自定义参数从变量注册到 PC catalog 的完整链路；
  4. 以 RM Studio PC Demo 验证 MockTransport、前后端通信、曲线和参数生命周期；
  5. 通过真实串口、带宽统计、丢帧统计、heartbeat 超时和 Runtime/Trace 检查并发与实时性；
  6. 对照用户操作过程处理刷新打断、写入误覆盖、目录分页失败、串口多线程抢读等问题；
  7. 固化协议版本、错误码、安全策略和存储状态，使后续不同机器人项目只需替换下位机注册内容。

8. 协议诊断工具

当你怀疑“到底有没有回包”时，可以使用原始 Probe：

```powershell

python protocol_probe.py COM8 --baud 921600 --tu-hello

python protocol_probe.py COM8 --baud 921600 --rm-hello

```

使用前关闭 RM Studio 对同一串口的连接。建议按以下顺序判断：

  1. 检查 COM 口、TX/RX/GND 和波特率；
  2. 发送 TU HELLO，确认参数协议；
  3. 发送 RM HELLO，确认监控协议；
  4. 对照原始十六进制帧、长度和 CRC；
  5. 最后再检查 UI 或前端显示。

10. 一个完整的整车电控观测示例

阶段 A：不接视觉，先验证云台控制器

在 KILL/SAFE 状态下检查零位、方向、限位和编码器角度。使用固定目标角输入，观察 target、angle、error、omega 和 output。此阶段只验证云台控制，不判断视觉效果。

阶段 B：接入视觉，但先不发射

确认 vision.online，观察视觉目标变化是否与画面中的目标运动一致。静止目标时，target 应基本稳定；目标移动时，目标角变化方向应与预期一致。此阶段优先处理坐标系和消息时序。

阶段 C：验证跟踪和预测

让目标以低速、可重复的方式移动，比较 target 和 angle 的相位差。若目标变化正常而实际角度滞后，检查控制输出和任务周期；若目标本身滞后，检查视觉处理延迟、消息时间戳和预测模块。

阶段 D：验证发射联动

在确认云台稳定后，再加入发射机构。记录目标角、云台角、视觉在线、系统模式和发射状态，检查开火时刻使用的是当前目标、预测目标还是过期目标。发射偏差不能简单归因于云台 PID，还需要检查弹道、枪管、摩擦轮速度和触发时序。

阶段 E：保存和复现

每次实验记录参数快照、设备固件版本、协议版本、视觉配置、Watch 变量、采样频率和测试条件。确认效果后才执行 Save，并重新连接检查 Saved 值是否保持。这样调参结果才能被复现和比较。

12. 项目边界与后续扩展方向

当前 RM Studio PC 已经覆盖整车参数调试、Selective Watch、PC 端触发记录、Execution Trace、RTOS Snapshot 和协议诊断。对于整车电控和视觉联调，还可以在协议约定稳定后扩展以下观测量：

  • 目标 ID、目标置信度和目标装甲板数量；
  • 视觉时间戳、图像帧号和端到端延迟；
  • 预测角、未预测角和预测时间；
  • 火控状态、开火许可和发射冷却状态；
  • 目标切换原因和锁定状态；
  • 云台限位、输出饱和和故障码。

这些扩展属于“让上位机更好地观测整车运行状态”，不等于把实时控制、视觉识别或并发调度算法搬进 RM Studio PC。保持下位机负责执行、上位机负责观测和调参的边界，才能让不同兵种、不同 MCU 和不同视觉方案复用同一个调试工具。


结语

整车系统的稳定性来自完整运行链路的验证：传感器输入要可信，控制数据要连续，视觉链路要可测量，云台和底盘反馈要一致，并发任务要满足实时性，通信数据还要能够追溯。RM Studio PC 的价值，就是把这些原本分散在代码、串口日志和示波器中的证据集中起来，让开发者能够沿着“下位机采集—协议发送—上位机接收—数据呈现—参数调整—任务验证”的链路逐项排查。

它不是一个只服务于自瞄的工具，也不是凭空生成控制效果的软件，而是一套面向 RoboMaster MCU 的整车电控调试基础设施。下位机负责采集、计算、调度和发送，上位机负责配置、查看、记录和分析，二者配合才能把整车系统从“能运行”推进到“可测量、可解释、可复现”。
