省流

Small Point-LIO 是 Point-LIO[1] 的重制版，以 MIT 协议开源。在相同参数下，性能大约比原代码快 2 - 3 倍。

代码仓库：https://github.com/yancey2023/small_point_lio

代码仓库国内镜像： https://www.yanceymc.cn/gitea/Yancey/small_point_lio

QQ 交流群：1070252119

考虑到这只是对现有技术方案的代码改进，所以我决定在赛季前期就把代码发布出来，供大家使用。

前言

本人大二时负责 25 赛季哨兵导航，目前大三，在 26 赛季同样在做导航相关技术研发。在我的 25 赛季 RM 生涯中，LIO 这个东西一直披着一层神秘的外衣，无论是数学原理还是代码实现，都晦涩难懂。虽然我对其内部结构有所了解，但是本着导航和决策才是重头戏的想法，我基本上还是把它当成一个盲盒在使用，从来没有认真重头梳理过 Point-LIO 的代码。本着穷究原理、洞悉本质的精神，我认真学习了其相关原理和代码实现，在这个过程中，我发现了 Point-LIO 原代码中有很多不合理的地方。为了让大家不再被原代码所折磨，于是这个项目诞生了。考虑到大家可能会被复杂的公式劝退，Point-LIO 的原理部分我就先跳过了，只给大家讲解改进的地方，但是我希望大家不要忽略原理的重要性，我之所以能做出 Small Point-LIO，肯定是从原理开始学习的。

数据预处理的改进

在 Point-LIO 中，为了去除异常点和降低计算量，会对点云进行过滤。我梳理了原代码的逻辑，有 4 种过滤方法同时进行：

  • 在 Mid-360 中，每个点都有一个 tag 字段，包含了各种探测属性下的置信度，可以根据这个过滤掉置信度较低的点云。
  • 根据点云距离进行过滤，最小距离和最大距离由 blind 参数和 det_range 参数控制
  • 每 N 个点取 1 个点，具体数量 N 由 point_filter_num 参数控制
  • 对点云进行体素降采样，具体栅格大小由 filter_size_surf 参数控制

同时，我认为原代码存在许多缺点：

  • 对于刚刚提到的参数，如果光看名字不看代码，是难以知道其作用的，但是当我们去看代码的时候，就会发现点云过滤逻辑分散在代码的各个地方，实在是让人摸不着头脑。
  • 原代码中，预处理部分还支持把多份点云进行合并、把单个点云拆分成多份点云，但是 Point-LIO 是逐点更新的，这对 Point-LIO 没有用。
  • 原代码包含了IMU预处理，这部分代码原本是 Fast LIO[2] 用来做点云去畸变的，但是 Point-LIO 是逐点更新的，不需要进行点云去畸变。
  • 原代码缓存了点云队列，但是 Point-LIO 是逐点更新的，不应该使用点云队列，而应该使用点队列。
  • 原代码还把点云和 IMU 数据打包成一次观测再进行后续处理，但是我认为这一步也是不需要的，直接从队列中获取数据进行后续处理可以使代码更加简洁。

基于以上思路，我重构了数据预处理部分：

  • 在接收到数点云时就进行各种点云过滤，把点和IMU存储在按时间排序的点队列和 IMU 数据队列中。
  • 对于点云的体素降采样，我在 small_gicp[3] 的点云降采样代码基础上进行修改，使降采样之后的点保留时间戳属性，且性能比 PCL 快 1.3 倍。
  • 考虑到大家可能需要去畸变后的稠密点云，我还把降采样前的点存储成队列，并在后续处理流程中进行去畸变操作并在话题中发布出来。

地图的改进

在滤波器的观测过程中，需要从地图中找到最近的 5 个点拟合成 1 个平面并计算残差，这里的找最临近点操作就是 Point-LIO 的性能瓶颈。在最初的代码中，原作者使用了 ikd-tree 作为地图，但是其实我们不需要严格地查询 K 近邻，所以原作者后续使用了 Faster-LIO[4] 提出的 iVox 作为地图。但是我发现 iVox 的代码实现仍然有不少可以改进的地方。我做了5件事来改进 iVox，同时，这也是 Small Point-LIO 性能优秀的关键之处。

改进 1

原代码中会在邻居中查找点，并把查找到的点和它到目标点的距离一起添加到候选列表中，如果候选列表的超过 5 个，就会把距离较远的点去掉。提前计算好距离确实能够提升根据距离排序的速度，但是在实际情况中，很多时候候选列表的点不会超过 5 个，这导致提前计算好距离这一行为白白浪费了性能。我在判断候选列表的点过多时才计算距离，使整个获里程计得了 40% - 60% 的性能提升。

改进 2

我发现哈希函数也是性能开销大头。原代码中的哈希函数如下：

template <>
inline size_t hash_vec<3>::operator()(const Eigen::Matrix<int, 3, 1>& v) const {
    return size_t(((v[0]) * 73856093) ^ ((v[1]) * 471943) ^ ((v[2]) * 83492791)) % 10000000;
}

原哈希函数确实很大程度上避免了哈希碰撞，但是我认为不适合里程计。实际过程中，雷达一段时间内扫出来的点总是在一定地图范围之内，不会同时出现相隔很远的点，如果我们走了很远，因为在新增栅格的时候如果容量超过阈值就会把时间最久远的栅格删除掉，所以远处的点基本已经被删除干净，不会造成影响。基于以上实际情况，我自己构思了一个哈希函数：

inline uint64_t hash_position_index(const Eigen::Matrix<uint16_t, 3, 1> &v) {
    return (static_cast<uint64_t>(v[0]) << 32) |
           (static_cast<uint64_t>(v[1]) << 16) |
           static_cast<uint64_t>(v[2]);
}

它只有简单的位运算，性能比原哈希函数优秀。它能在数值溢出的时候与之前的另一端的边界衔接上，从而有效利用了空间。它还能通过简单的数学计算就得到邻居栅格的哈希值，不需要根据邻居栅格的坐标重新计算哈希值。这大幅优化了性能，使整个里程计获得了 30% - 40% 的性能提升。

你也许会想一些极端情况，比如地图分辨率是 0.01m 且雷达扫描能扫一千米，那确实会受到哈希冲突的影响，但是我们一般会把里程计地图分辨率设置在 0.1m 以上，不会把里程计地图分辨率设置得这么低，所以从实践上来看是不会有影响的。

改进 3

我把哈希表从 std::unordered_map 改为了 ankerl::unordered_dense::map 。性能更好的哈希表实现大幅优化了代码性能，使整个里程计获得了 10% - 20% 的性能提升。

改进 4

原代码中，每个栅格都使用了 std::vector进行点的存储，但在实际情况中，我们往往会避免在单个栅格中存储多个点。因此我们可以让每个栅格直接存储一个点，简化了数据结构。

改进 5

原代码中， iVox 中有 LRU 缓存，它可以在地图过大时删除历史久远的栅格，从而控制住了地图的内存占用。但是它在判断不需要把点添加到地图中的时候，不会更新 LRU 缓存，我认为这并不是最优的策略。因此，我修改了其逻辑，如果点对应的栅格已经存在地图中，也会把该栅格更新到 LRU 缓存前面，从而提升里程计稳定性。

滤波器的改进

在point_lio的原代码中，相同时间的点会一起更新，我们无法提前得知一次更新的点数量，导致观测结果的矩阵维度不是固定的。但是经过测试，我发现过滤后的 Mid-360 点云中相同时间的点极少，所以我们可以把相同时间的点分多次更新，把观测结果的矩阵维度改为固定值，这样就可以把代码实现中的 Eigen::Dynamic 改为具体数字，使整个里程计获得了 20% - 30% 的性能提升。

同时，我没有使用 IKFoM 框架，而是重头实现了相应的代码，代码的易读性更好。

编译选项的改进

通过增加以下编译选项，可以让代码性能得到大幅度提升。这部分没什么技术含量，就不深入解释了，最主要的是让编译器根据你的 CPU 进行特定的优化 。不过以防万一，我还是说明一下，我之前的性能对比都是与加了该编译选项的 Point-LIO 进行对比的。

if (CMAKE_CXX_COMPILER_ID STREQUAL "GNU" OR CMAKE_CXX_COMPILER_ID STREQUAL "Clang")
    add_compile_options("-march=native")
    add_compile_options("-ffast-math")
    add_compile_options("-fno-math-errno")
endif()

结语

不知道大家看完上述内容是什么感受，也许会大受震撼，也许是觉得这些改进都很平常。但我却在思考一个问题：既然有这么多可以优化的地方，为什么 Point-LIO 出来了这么久都没人去做优化呢？我认为大家都只是把 Point-LIO 当成一个工具在使用，就算是抱着学习的心态去看 Point-LIO 的代码，也没有思考它的代码是否合理。技术的进步来自每一位工程师对于现有方案的思考和改进，我们去阅读代码时，不仅是要看这段代码实现了一个什么功能，更是要去思考它这么做的本质的是什么，只有这样，才能洞悉改进的方向，做出更好的作品。希望这能对你有所启发，在之后的学习生涯中发扬这穷究原理、洞悉本质的精神。
