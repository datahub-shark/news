一分钟了解 RPL：快速的集成与使用

RPL 的设计哲学是“让使用者少写代码，让 CPU 少做无用功”。它极其容易集成，且在嵌入式平台（如 STM32）上能够优雅地实现低延迟的协议解析。

1. 极简引入（支持单文件头）

无论你是使用 CMake 的现代工程，还是使用 Keil/IAR 的传统工程，RPL 都提供了零门槛的接入方式。你可以通过 CMake FetchContent 引入，或者直接将自动生成的单文件头 RPL.hpp 拖入工程，无需配置任何路径，开箱即用。

你还可以一并引用我们做好的开箱即用的裁判系统包头文件。

2. 核心运转模式：DMA 零拷贝写入 + O(1) 无锁读取

以 STM32 串口接收为例，传统的做法需要繁琐的接收中断和双缓冲切换。而在 RPL 中，底层逻辑被简化到了极致：

#include "RPL.hpp"
#include "MyPackets.hpp" // 你的数据包定义

// 1. 全局实例化解析器与内存池
RPL::Deserializer<PacketA, PacketB> deserializer;
RPL::Parser<PacketA, PacketB> parser(deserializer);

// 2. 底层中断：开启 DMA 直接写向 RPL 内部连续内存
void start_dma_receive() {
    auto span = parser.get_write_buffer(); // 获取 RPL 内部可用连续内存
    HAL_UART_Receive_DMA(&huart1, span.data(), span.size());
}

// 3. 底层中断：DMA 接收完成，通知解析
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart) {
    if (huart->Instance == USART1) {
        size_t received_len = ...; // 获取实际接收长度
        parser.advance_write_index(received_len); // 框架自动触发解析、CRC校验与入池
        start_dma_receive();
    }
}

// 4. 上层业务：主循环中随时无锁获取最新数据
void control_loop() {
    while(1) {
        auto pkt = deserializer.get<PacketA>(); // O(1) 提取，绝对安全且已内存对齐
        if (pkt.mode == 1) { /* 执行控制逻辑 */ }
    }
}

仅需数行代码，底层的内存回绕、帧头搜索、多重 CRC 校验、状态同步已被 RPL 完美接管。

为什么我们要造这个轮子？

在过去的开发中，我们发现传统的底层通信解析方案在面对日益复杂的机器人系统时，往往会暴露出一些工程上的痛点：

  1. 冗杂的状态机与硬编码： 面对裁判系统几十种不同命令码的数据包，传统解析往往依赖长篇的 switch-case 结构和大量的内存拷贝操作。不仅代码臃肿，而且在官方更新协议时维护成本极高。
  2. 偶发的数据截断与校验失败： 传统的 RingBuffer 在缓冲区首尾回绕时经常发生“数据包截断”，将完整帧物理分割。如果没有妥善的拼接逻辑，极易导致 CRC 校验失败，这也是大家常遇到的“偶发性裁判系统数据读取失败”的原因之一。
  3. 跨端同步与对齐差异： 在研发上下位机（STM32 与 MiniPC）自定义协议时，双端的结构体对齐（Alignment）和位域解析经常导致隐蔽的解析Bug，联调过程相对低效。

为了彻底解决这些问题，我们决定推翻重来。我们引入了 BipBuffer 来保证底层内存的绝对连续性，并深度运用 C++20 编译期元编程技术，打造了 RPL 框架。我们把一切能让编译器做的事（例如哈希映射、位域掩码计算）全部转移到了编译期，从而换取趋近于零的运行时开销。

RPL 能为你做什么？

RPL 采用了干净的“纯字节流抽象”设计。无论是串口 DMA、USB 还是 UDP，开发者只需传入字节流，底层的解析与路由均由框架自动完成。

1. 裁判系统 & VT03 图传链路：“开箱即用”

借助模板的扩展性，RPL 能够以一致的接口兼容异构协议。无论是传统的裁判系统，还是今年数据帧定义完全不同的 VT03 图传链路，开发者都无需手动编写底层状态机，只需调用：

parser.push_data(rx_buffer, len);

底层会自动完成拆包、多重 CRC 校验与 O(1) 复杂度的路由分发。

2. “零开销”的底层链路健康监控

线缆松了？图传断了？RPL 内置了基于模板策略模式的 ConnectionMonitor。你可以在业务层随时调用 parser.is_connected(100) 检查是否超过 100ms 未收到数据，从而让底盘或云台迅速切入安全降级模式（如停止自瞄、底盘锁死）。不需要此功能时，编译器会将其优化为 0 开销。

3. Web 图形化协议生成器

我们开发了一个配套的 在线协议可视化编辑器。
针对上下位机自定义协议的需求，开发者可通过图形界面直观地分配数据包类型与位段长度。
工具会自动生成符合 RPL 规范的头文件，STM32 和 MiniPC 两端只需引入同一文件，即可保证完美的解析和严格的内存对齐，从根源上消除双端通信不一致的隐患。

4. “数据黑板”与无锁状态获取

RPL 的内存池底层采用 SeqLock（顺序锁） 机制。底层解析线程并发写入的同时，控制算法线程可以在任何位置直接获取数据：

auto chassis_data = deserializer.get<ChassisControl>();

该操作为 O(1) 复杂度，既保证了数据校验的安全性与严格的 CPU 对齐，又避免了互斥锁带来的线程阻塞等待，永远提供最新鲜的有效状态。

性能基准测试

“优雅”不能以牺牲性能为代价。我们在 x86 平台和 ARM Cortex-M3 (Zephyr 模拟器) 上均做了基准测试：

  • x86 (i7-1185G7):
    • 数据包反序列化 (get 读取): 0.526 ns（仅需十几条汇编指令）
    • 小包完整解析 (含拆包 + CRC8/16 校验 + 入池): 75.0 ns
  • ARM (Cortex-M3 @ 480MHz 估算):
    • 数据包反序列化: 23 ns
    • 配合 DMA 完整帧写入解析: 904 ns

即便在 1000Hz 的极高频控制回路下，RPL读取数据包的开销也仅占 CPU 时间的万分之一。
