一、技术背景概述

1、 控制逻辑研发与优化

25赛季中，工程机器人仅对6个关节进行PID控制，未完成解算/前馈/前向，在控制时抖动明显。所以在26赛季中，最主要的目标是完成工程机器人串联式机械臂的建模、解算与控制，让机械臂运动得更流畅。

      负责部分：本人负责机械臂的建模、通用串联机械臂控制框架开发，并以此基础进行工程机器人的软件开发。

2、自定义控制器优化

25赛季中，自定义控制器采用了同构的方案，效果不错且开发难度相对较低。所以当前赛季决定使用延续同构方案。由于自定义控制器的体积和重量相对较大，为了操作手操作顺畅，将25赛季的磁编方案换为电机方案，并加上重力补偿来优化操作手的操作手感，

负责部分：本人负责自定义控制器的建模、解算、控制以及软件编写。

3、架构优化与探索

由于26赛季初期规划时，采用了7轴机械臂作为工程机器人的大臂，而选取的机械臂构型较为特殊，无解析解。而数值方法对于下位机来说计算压力很大，且队内的嵌入式调试软件仅有Ozone，可视化途径只有图表。对于机械臂的调试不友好。且无法记录日志，复现一些程序问题时较为困难。而且在25赛季中，上下位机通信存在较大延迟。基于此，在26赛季中，采用自行开发的无传统下位机的控制架构作为工程机器人的控制架构。

负责部分：本人负责无传统下位机控制架构开发、USB2Everything固件的开发与USB2Everything下位机pcb绘制。

4、机械臂与科技核心的对抗和装配失败的避免

在26赛季中，造出科技核心与资源区后，我们便发现了机械臂和资源区/科技核心刚性对抗，导致电机过温失能的问题。且能量单元吸附在科技核心后，如果被意外拔出，会被判定为装配失败。于是引入柔顺控制解决这一问题。

     负责部分：本人负责柔顺控制的实现。

二、技术详细方案

(1) 技术方案调研和对比

上位机的选取[5]

在26赛季工程机器人控制架构设计初期，面临的核心问题是如何在无传统下位机架构下，实现多关节电机的高频通信、低延迟控制以及便于调试的算法运行环境。由于工程机器人采用串联式机械臂构型，控制系统需要同时承担关节状态采集、运动学解算、前馈补偿、柔顺控制以及上层交互等任务。如果仍沿用传统上位机规划+下位机执行的方式，一方面会受到上下位机通信延迟和调试手段受限的影响，另一方面也不利于机械臂控制的快速迭代。

调研阶段主要比较了四类方案：自带 CAN 外设的 ARM 开发板方案、UART 转 CAN 方案、普通字符设备 USB 转 CAN 方案，以及本项目最终采用的 USB2CAN / UART 设备映射至上位机 SocketCAN / tty 字符设备的方案。各方案对比如下

1、 自带CAN外设的 ARM 开发板  

使用具备 CAN 控制器的 ARM 开发板作为下位机，但是高算力开发板成本较高，低成本开发板算力不足，受限于本赛季的经费限制，舍弃这一选项

2、 UART 转 CAN

通过单片机的串口转发CAN报文，硬件简单，开发门槛低，成本较低，但是UART 带宽有限，无法支撑双路 1 Mbps CAN 总线的高负载通信，故舍弃这一选择

3、普通字符设备 USB 转 CAN

通过USB转发CAN 报文，以字符设备形式暴露给 Linux 上位机，需要自行处理 CAN 帧封装、时间戳、收发队列和异常恢复，调试方式不直观，不利于快速定位通信问题

4、（本项目首次提出）下位机通过 USB 将板载外设映射到 Linux 原生接口

将下位机的CAN通过usb映射为SocketCAN 接口，将下位机其他串口外设映射为 tty 字符设备，由上位机统一管理。能直接使用can-utils和minicom的工具调试，便于日志记录、回放和问题复现。但是需要在驱动层完成设备映射、通信抽象层。由于调试便利，后续维护成本极低，最终采用该方案。

冗余机械臂的逆运动学

      由于26赛季初赛季方案制定工程机器人机械臂为7轴机械臂，且构型特殊，无完整解析解，所以只能从数值方法入手。查询相关领域综述文献[1]，大致可以总结出三种方案：

1、 Jacobian转置梯度下降

Jacobian的定义是f(θ)=(∂si∂θj)ijf(\theta) = (\frac{\partial s_{i}}{\partial \theta_{j}})_{ij}，描述关节速度到末端速度的一阶线性映射，定义一个误差向量，Jacobian 转置法利用JTeJ^T e构造误差函数的下降方向。优点是稳定；缺点是未对冗余轴建模，在迭代过程中可能造成机械臂在冗余自由度内自旋，以及迭代速度较慢，对于算力要求较高，在赛季中迭代时舍弃了这一选择。

2、 伪逆迭代

Jacobian 转置梯度下降虽然实现简单、数值上较稳定，但其本质上只是利用JTeJ^Te构造下降方向，在7轴冗余机械臂中，该方法收敛速度较慢，而且对冗余自由度缺少明确约束，在外力的作用下，如果外力造成的误差恰好有机械臂此时的零空间分量，在迭代过程中将会出现冗余关节自旋。

伪逆迭代将逆运动学问题写成当前位姿附近的线性近似：e≈JΔθe \approx J \Delta \theta

由于 7 轴机械臂的 Jacobian 通常不是方阵，无法直接求逆，因此使用 Moore-Penrose 伪逆求解关节角增量：

Δθ=J#e\Delta \theta = J^{\#}e                                                                         (1.1)

对于冗余机械臂，还可以进一步利用零空间分解[1]：

Δθ=J#e+(1−J#J)ϕ\Delta \theta = J^{\#}e + (1 - J^{\#}J)\phi                                                                  (1.2)

相比 Jacobian 转置法，伪逆迭代需要的迭代次数更少，且对零空间进行了建模，允许在零空间内设置任务来唯一确定关节角。但是伪逆在Jacobian奇异时数值不稳定，容易振荡，故在机械臂研发迭代时被舍弃。

3、 阻尼伪逆迭代

阻尼伪逆迭代在伪逆法的基础上加入阻尼项

minΔθ(∣JΔθ−e∣2+λ2∣Δθ∣2)min_{\Delta \theta}(| J \Delta \theta - e |^2 + \lambda^2 |\Delta \theta|^2)                                                             (1.3)

阻尼伪逆的缺点是需要选择合适的阻尼系数。综合考虑收敛速度、奇异位姿鲁棒性，最终采用阻尼伪逆迭代作为7轴机械臂IK的方案

(1) 软件系统架构

在设计上，架构的核心思想是线程解耦+模块api通用。线程间通过轻量化的多生产者多消费者消息分发机制解耦。同时，同类型外设驱动继承自统一的基类接口，以保证驱动模块在调用方式、生命周期管理和功能扩展上的一致性。

在调试方面，架构提供了终端打印、Foxglove可视化调试以及日志文件写入的途径，便于在开发和实车运行过程中对各外设状态、通信数据和异常信息进行观测追踪。上位机的软件控制框架如下：

(1) 功能和性能指标的定义

1、CAN 回环延迟

CAN 回环延迟用于衡量上位机经 SocketCAN 接口发送一帧 CAN 报文后，经过 USB2CAN 设备、驱动映射层和系统接收队列重新回到上位机所消耗的总时间。反映了 USB2CAN 设备映射、驱动封装、内核收发队列以及上位机调度延迟的综合影响

测试时，上位机在发送 CAN 报文时记录时间戳tsendt_{send}，在接收到对应回环报文时记录时间戳trecvt_{recv}，则单帧 CAN 回环延迟定义为

TCanLoop=trecv−tsendT_{CanLoop} = t_{recv} - t_{send}                                                              (3.1.1)

测试过程中连续发送100 0000帧 CAN 报文，统计平均延迟、最大延迟、95% 分位延迟和延迟抖动。其中平均延迟定义为

    T=1N ∑TiT=\frac{1}{N}\ \sum T_i                                                                       (3.1.2)

延迟抖动可用标准差表示：

σCAN= 1N∑i=1N(Ti−TCAN)2 \sigma_{CAN}=\ \sqrt{\frac{1}{N}\sum_{i=1}^{N}\left(T_i-T_{CAN}\right)^2\ }                                                          (3.1.3)

该指标的目标是保证 CAN 回环延迟稳定在控制周期允许范围内。若机械臂控制周期为 ，则应满足

TCanLoop95%<TctrlT_{CanLoop}^{95\%}<T_{ctrl}                                                                  (3.1.4)

即至少95%的CAN通信回环延迟小于一个控制周期。以约8000fps的收发包速率测试，程序实测输出结果如下

Tbus,min=1111×106=111 μsT_{bus,min}=\frac{111}{1\times{10}^6}=111\ \mu s                                                           (3.1.6)

2、CAN 的负载测试

CAN 负载测试用于验证 USB2CAN 设备在高频的报文收发场景下是否能够稳定支撑多电机通信需求。由于工程机器人机械臂包含多个关节电机，控制过程中需要周期性发送控制指令并接收电机反馈，因此 CAN 总线需要在较高负载下保持低丢帧率和稳定延迟。

在实际测试中，可通过逐步提高 CAN 报文发送频率，记录不同负载率下的丢帧率、错误帧数量、平均延迟和最大延迟。丢帧率定义为

ropRateCAN=Nsend−NrecvNsend× 100%ropRate_{CAN}=\frac{N_{send}-N_{recv}}{N_{send}}\times\ 100\%                                                      (3.2.1)

其中为NsendN_{send}发送帧数量， NrecvN_{recv}为成功接收帧数量。

这个指标用于判断系统在双路1Mbps的CAN总线高负载通信下的稳定性。理想情况下，在满足机械臂控制频率要求的报文负载下，系统应保持无明显丢帧、无持续错误帧，并且延迟波动不影响控制周期。下表是回环测试的部分结果

3、实际 USB 带宽与理论 USB 带宽的差异

为了评估通信架构的带宽利用情况，定义 USB 实际有效带宽为单位时间内上位机与 USB设备之间成功传输的有效数据量：

BUSBreal=DatavalidTB_{USB_{real}}=\frac{Data_{valid}}{T}                                                                  (3.3.1)

其中 为测试时间T内实际成功传输的有效载荷数据量。USB 带宽利用率定义为

ηUSB=BUSBrealBUSBtheory×100%\eta_{USB}=\frac{B_{USB_{real}}}{B_{USB_{theory}}}\times100\%                                                               (3.3.2)

其中BUSBtheoryB_{USB_{theory}}为理论USB带宽。为这个指标用于说明理论 USB 带宽与实际通信能力之间的差距。对于USB2CAN/UART而言，关注重点是验证在工作时，USB 链路不会成为系统瓶颈。以及评估自定义bulk协议的USB带宽的利用率。

在 CAN 回环负载测试中，程序以约7500fps的速率进行报文收发。测试过程中，通过 USB 带宽监测工具测得 USB2CAN 设备的实际有效带宽约为：BUSB,real=1092.93,kb/sB_{USB,real}=1092.93,kb/s。按照USB FS的理论带宽计算，则 USB 带宽利用率为：ηUSB=1092.9312000×100%≈9.11%\eta_{USB}=\frac{1092.93}{12000}\times100\%\approx9.11\%。由此可见，在的 CAN 回环负载下，USB的有效带宽利用率仍远低usbfs 的理论带宽上限，说明 USB 物理链路本身并不是主要瓶颈。

1、 机械臂的控制

机械臂的建模

工程机器人采用7轴串联式机械臂，需要在遥控、自定义控制器和自动装配任务之间切换。25赛季仅依赖关节 PID 控制时，机械臂在负载变化和姿态切换时容易出现跟踪误差、抖动，因此控制目标不应该是单纯让电机到角度，而是建立从任务空间目标、逆解算、轨迹插值到关节力矩控制的完整控制模型。

实现上，26赛季将机械臂控制拆成控制线程和 IK 线程，控制线程负责读取遥控器、自定义控制器、末端力矩、关节反馈和状态机；IK 线程负责根据目标末端位姿输出下一步关节角。由于动力学参数不准确，控制律采用动力学前馈+关节PD/串级PI位置环+PD速度环补残差的形式：

τ=M(q)qd¨+C(q, q˙) q˙+G(q)+K⁡p(q⁡d−q)+K⁡d( qd˙− q˙)\tau=M\left(q\right)\ddot{q_d}+C(q,\ \dot{q})\ \dot{q}+G(q)+\operatorname{K}_p(\operatorname{q}_d-q)+\operatorname{K}_d(\ \dot{q_d}-\ \dot{q})                                     (4.3.1)

τ=M(q)qd¨+C(q, q˙) q˙+G(q)+PD( PI(q⁡d−q)− q˙)\tau=M\left(q\right)\ddot{q_d}+C(q,\ \dot{q})\ \dot{q}+G(q)+PD(\ PI(\operatorname{q}_d-q)-\ \dot{q})                                       (4.3.2)

其中M(q)qd¨+C(q, q˙) q˙+G(q)M\left(q\right)\ddot{q_d}+C(q,\ \dot{q})\ \dot{q}+G(q)是由Newton-Euler递推求得的动力学方程，用于补偿机械臂本体动力学。PD/串级PI+PD 用于抑制模型不准确带来的残余误差。C(q,q˙)C\left(q,\dot{q}\right)在公式中显式写出，但在实现中，求解的是C(q,q˙)q˙C\left(q,\dot{q}\right)\dot{q}而非C(q,q˙)C\left(q,\dot{q}\right)。轨迹层采用任务空间插值与关节空间插值结合，任务空间中位置按线段插值，姿态按四元数 Slerp 插值；关节空间中使用五次多项式生成 (q, q˙, q¨)(q,\ \dot{q},\ \ddot{q})，五次多项式的末状态速度与加速度为0。再送入力矩控制。这样可以避免直接跳变目标角造成瞬时力矩冲击。

通用串联式机械臂的定义与通用正逆解

通用串联式机械臂的定义

工程机器人采用串联式机械臂，不同赛季、不同任务中机械臂的自由度数量、关节排列顺序、关节轴方向和末端执行器结构都可能发生变化。若每更换一次机械结构都重新推导一套正逆运动学公式，会导致软件与机构强绑定，后续维护和迭代成本较高。因此，26赛季中将机械臂抽象为一组按顺序连接的关节数组，而不是固定写死为某一种 yaw-pitch-pitch-roll 构型。对于一个 n 自由度串联式机械臂，其关节变量可表示为：

q=[q1q2⋯qn]Tq=\left[\begin{matrix}q_1&q_2&\cdots&q_n\end{matrix}\right]^T

其中表示第i个关节的逻辑关节量。对于旋转关节，为关节角；对于平移关节，为关节位移；对于固定关节，不参与运动，只提供固定坐标变换。程序中每个关节由关节类型、关节轴、零位变换、关节限位、电机对象、质量、质心、惯量和摩擦参数共同描述。因此机械臂的定义可以写成：

Jointi={Ti0, typei, axisi, qmin,i, qmax,i, motori, mi, rc,i, Ii, frictioni}Joint_i=\left\{T_i^0,\ type_i,\ axis_i,\ q_{min,i},\ q_{max,i},\ motor_i,\ m_i,\ r_{c,i},\ I_i,\ friction_i\right\}                       (4.3.3)

其中 Ti0T_i^0 是第i个关节相对于上一个关节的零位固定变换，typeitype_i表示关节类型，axisiaxis_i表示该关节绕局部坐标系中的哪一个轴运动。这样定义后，机械臂的构型由关节数组决定，而不是由某一套固定公式决定。当机械臂从6轴改为7轴，或某个关节轴方向发生改变时，只需要修改关节定义，不需要重写完整的运动学框架

通用正运动学

正运动学用于解决已知关节角，求末端位姿的问题。机械臂末端位姿由位置和姿态共同组成，可以使用齐次变换矩阵表示：

T=[Rp01]T=\left[\begin{matrix}R&p\\0&1\end{matrix}\right]                                                                        (4.3.4)

其中R为末端姿态旋转矩阵，p为末端在基座坐标系下的位置。对于第i个关节，程序先叠加该关节的零位固定变换Ti0T_i^0，再根据关节类型和关节轴叠加运动变换 Ai(qi)A_i\left(q_i\right)。因此通用串联式机械臂的末端位姿可以写为：

Te(q)=T10A1(q1)T20A2(q2)⋯Tn0An(qn)T_e\left(q\right)=T_1^0A_1\left(q_1\right)T_2^0A_2\left(q_2\right)\cdots T_n^0A_n\left(q_n\right)                                              (4.3.5)

其中Ai(qi)A_i\left(q_i\right)由关节类型决定。若该关节为旋转关节，则Ai(qi)A_i\left(q_i\right)为绕X、Y或Z轴的旋转矩阵；若该关节为平移关节，则Ai(qi)A_i\left(q_i\right)为沿X、Y或Z轴的平移矩阵；若该关节为固定关节，则只使用固定变换。程序中从单位位姿开始，按照关节数组顺序依次 Compose 每个关节的变换，最终得到末端执行器相对于 base 坐标系的位姿。

这种正解方式没有使用特定构型的几何关系，也不依赖某一套人工推导的解析公式。只要每个关节的零位变换、关节类型和关节轴定义正确，程序就可以计算任意串联构型的末端位姿。因此，正运动学部分具有较好的通用性。

1、 柔顺控制[2][3]

   本赛季机械臂采用动力学模型前馈与PI 位置环PD 速度环的串级 PID 位置控制框架，通过动力学前馈补偿主要负载，利用反馈环节修正模型未建模的误差。由于在能量单元装配过程中，机械臂末端需要与科技核心发生接触和对准。如果仍采用刚性位置控制，当末端位姿与目标装配位置存在偏差时，位置环会持续增大输出以消除误差，容易导致关节电机过热

   在意识到该问题时，赛季已经进入中后期。如果直接将原有位置控制框架改为基于τ=JT F\tau=J^T\ F的任务空间力控制框架，则需要十分准确的动力学参数。因此，在不大幅改变原有控制架构的前提下，本赛季最终选择在位置控制框架上引入柔顺控制，尽量减小装配接触过程中的刚性对抗

柔顺控制主要包括阻抗控制和导纳控制两类方案。最终，本赛季选取导纳控制框架，而非直接采用阻抗控制。原因是赛季中规划的自动装配任务要求末端能够最终能大致收敛到一个指定位姿。导纳控制主要根据外部接触力对期望位置或期望速度进行修正，更容易和现有的位置控制框架结合，改动成本比较低。

任务空间柔顺

任务空间的导纳控制是在末端模拟一个6自由度的弹簧-质量块-阻尼系统，根据估算的外力来计算在外力作用下虚拟弹簧的响应，从而影响末端的位姿。

设原始期望末端位姿为Td=[Rdpd01]T_d=\left[\begin{matrix}R_d&p_d\\0&1\end{matrix}\right],导纳修正后的末端位姿为Ta=[Rapa01]T_a=\left[\begin{matrix}R_a&p_a\\0&1\end{matrix}\right]。为了让平移和旋转误差都在同一个虚拟系统中描述，将导纳状态定义x = {Δpx Δpy  Δpz Δψ Δθ Δϕ}Tx\ =\ \left\{\mathrm{\Delta}p_x\ {\mathrm{\Delta p}}_{y\ }\ \mathrm{\Delta}p_z\ \mathrm{\Delta\psi}\ \mathrm{\Delta\theta}\ \mathrm{\Delta\phi}\right\}^T。其中前三项表示当前导纳位姿相对于目标位姿的末端坐标系下平移偏差：Δp=RdT(pa−pd)\mathrm{\Delta p}=R_d^T\left(p_a-p_d\right)后三项由相对旋转矩阵RdTRaR_d^TR_a转换为欧拉角得到，即表示当前导纳位姿相对于目标姿态的姿态偏差。理想情况下，末端应回到原始目标位姿，所以导纳系统的目标状态为xd=0,x˙d=0,x¨d=0x_d=0,\dot{x}_d=0,\ddot{x}_d=0。任务空间导纳的基本形式可以写作

Ma(x¨−x¨d)+Ba(x˙−x˙d)+Ka(x−xd)=FextM_a\left(\ddot{x}-{\ddot{x}}_d\right)+B_a\left(\dot{x}-\dot{x}d\right)+K_a\left(x-x_d\right)=Fext                                           (4.5.1)

在本赛季中，导纳的目标状态为静止状态。对第 (i) 个自由度，有：

x¨i=Fext,i−Bix˙i−KixiMi\ddot{x}i=\frac{Fext,i-B_i{\dot{x}}_i-K_ix_i}{M_i}                                                                (4.5.2)

其中 (Mi,Bi,Ki) \left(M_i,B_i,K_i\right)分别是该方向上用于模拟虚拟弹簧-质量块-阻尼系统的参数。为了避免微小噪声持续驱动导纳系统，在控制系统中加入死区，然后使用离散形式对导纳状态进行更新：

{x˙k+1=x˙k+12(x¨k+x¨k+1)Δtxk+1=xk+x˙kΔt+12x¨k+1Δt2\left\{\begin{matrix}{\dot{x}}_{k+1}={\dot{x}}_k+\frac{1}{2}\left({\ddot{x}}_k+{\ddot{x}}_{k+1}\right)\mathrm{\Delta t}\\x_{k+1}=x_k+{\dot{x}}_k\mathrm{\Delta t}+\frac{1}{2}{\ddot{x}}_{k+1}\mathrm{\Delta}t^2\end{matrix}\right.                                                     (4.5.3)

这样可以将估计到的末端外力转换成下一周期的导纳位姿偏移量。得到新的xk+1x_{k+1}后，再将其重新转换回末端位姿Ta=TdΔT(x)T_a=T_d\mathrm{\Delta T}\left(x\right)。其中由平移偏差和姿态偏差组成。之后可以将TaT_a作为新的 IK 目标，经过阻尼伪逆 IK 解算得到关节目标角，再进入原有的关节空间轨迹插值和动力学前馈控制链路。

外力估计方面，由于本赛季的经费限制，不选择使用六维力传感器，而是利用关节力矩反馈反推末端 wrench。由虚功关系τ=JTF\tau=J^TF，当机械臂为 7 自由度且JTJ^T不是方阵时，不能直接求逆。因此使用阻尼伪逆形式估计末端受力：

F^=(JJT+λ2I)−1Jτ\hat F = \left(JJ^T+\lambda^2I\right)^{-1}J\tau                                                               (4.5.4)

为了尽量去掉机械臂自身重力、惯性和科氏项的影响，程序中分别计算由电机反馈力矩得到的末端受力和由动力学模型前馈力矩得到的末端受力，并取二者差值作为外界接触力估计：

F^ext=LPF2f((JJT+λ2I)−1Jτreal−(JJT+λ2I)−1Jτmodel)\hat F _{ext} = LPF2f\left(\left(JJ^T+\lambda^2I\right)^{-1}J\tau_{real}-\left(JJ^T+\lambda^2I\right)^{-1}J\tau_{model}\right)                                    (4.5.5)

其中(LPF2f(⋅))\left(LPF2f\left(\cdot\right)\right)表示二阶巴特沃斯滤波器，选取频率的方法为：在机械臂运动时对机械臂施加某些方向上的恒力，采集数据后进行Fourier变换，选取其中较低频作为最终得到的估计外力。

但是在实际测试中，任务空间柔顺没有作为最终方案采用。因为该方法对动力学模型精度要求太高。而本赛季中没有完整研究出自动动力学标定的方法，实际动力学参数由SolidWorks导出后手动微调得到。机械臂的质量、质心、摩擦、减速器传动效率和电机力矩反馈必然存在误差，所以τreal−τmodel\tau_{real}-\tau_{model}中不仅包含外界接触力，也包含模型误差、摩擦误差、减速机构误差和传感器噪声。这个残差再经过 J的阻尼伪逆映射到任务空间后，会被进一步放大，在 Jacobian 条件数较差或接近奇异位姿时更加明显。会导致导纳系统会把噪声误认为真实外力，生成抖动的末端目标位姿；该目标位姿再经过 IK 解算，会进一步造成关节目标角抖动。虽然调高虚拟弹簧-阻尼-质量块的虚拟质量参数可以减缓抖动，但毕竟只是权宜之计，无法根治，所以放弃任务空间的导纳框架。

本赛季中任务空间导纳主要完成了外力估计、导纳位姿计算和调试可视化，用于验证任务空间柔顺的可行性。但由于动力学参数不够准确，最终没有将其作为主控制中的闭环目标

关节空间柔顺

关节空间柔顺的思路与任务空间柔顺差不多，只是将柔顺控制从末端位姿层下沉到关节角。与任务空间柔顺相比，关节空间柔顺不再先估计末端六维外力，也不需要将外力通过 Jacobian 反解到任务空间，而是直接利用每个关节上的残余力矩来修正该关节的期望角度。这样做虽然不能保证末端在笛卡尔空间中具有严格各向同性的柔顺特性，但实现更短，对动力学模型和 Jacobian 条件数的依赖更弱。

不过，关节空间柔顺也存在局限。由于柔顺方向定义在关节空间中，而不是末端笛卡尔空间中，同样的关节偏移在不同姿态下对应的末端位移方向不同，因此它不能像理想任务空间导纳那样直接指定末端在x,y,z,roll,pitch,yaw六个方向上的柔顺特性。但考虑到本赛季动力学参数仍存在较大误差，任务空间力估计噪声较大，关节空间柔顺在工程实现上更加稳定、改动更小，也更容易与已有的动力学前馈和串级 PID 位置控制框架结合。因此，最终采用关节空间柔顺作为本赛季机械臂接触缓冲和自定义控制器操作优化的主要方案。

(1) 不足之处

本赛季中，本人完成了一套无传统下位机的 Linux 上位机软件架构开发、USB2CAN/UART 下位机固件开发以及与之配套的 Linux 上位机驱动开发。基于此，进一步实现了一套兼容任意串联式机械臂构型的完整建模与软件控制框架，并基于此框架完成了工程机器人以及自定义控制器的开发，同时对自动装配进行了初步探索。

然而，由于该系统涉及实时 Linux 架构、USB 复合设备驱动、下位机固件、机械臂建模与控制等多个领域，当前的上下位机设计与控制系统仍存在一些不足，后续仍需继续迭代和完善

上位机架构

当前上位机架构在工程化和自动化程度上仍有不足。系统部署仍依赖dpkg手动安装实时内核、通过 insmod 加载内核模块，额外配置 systemd 服务实现自启动，未形成统一的全局控制脚本或管理程序，存在一定操作成本。

同时，在架构中新增功能模块需要手动修改 CMakeLists.txt、添加预设并新建对应目录，不符合自动化框架的设计预期，也不太利于快速切换不同机器人代码预设。后续需要进一步完善模块生成、编译配置和运行管理流程，使其更符合可扩展软件框架的定位

在可视化和调试方面，当前架构接入了 Foxglove SDK，但对部分自定义数据类型和一些复杂变量结构的支持仍不够完善，需要进一步封装与适配。相较于 ROS 2，本架构的主要优势在于实时性。基于 Preempt-RT 补丁的 Linux 实时内核，以及轻量化的多生产者-多消费者消息分发机制，线程间通信延迟能够明显低于 ROS 2 节点间通信延迟的量级[7]。但与此同时，本架构对 ROS 2 生态的兼容仍不成熟，尚处于探索阶段，导致现阶段难以直接复用 ROS 2 中成熟的算法、工具链和调试生态

后续的改进是在当前架构的基础上，继续优化代码逻辑；编写自启的开关脚本、切换配置的gui脚本程序；以及调试对ROS的兼容

上位机驱动与下位机固件

上位机驱动与下位机固件是本赛季中技术风险最高的部分。上位机驱动的整体设计借鉴了 gs_usb 的实现思路[6]，但在当前版本中省略了错误帧上报机制。当 CAN 总线出现异常时，主要由下位机固件自行处理错误并尝试重启总线。该设计在一定程度上减少了上位机侧的控制复杂度，但也削弱了用户态对总线状态的观测与干预能力，不利于进行总线级别的debug。

此外，下位机固件基于队内嵌入式框架LibXR开发，但当前所使用的 LibXR 版本并非最新版本。如果后续希望推行新版固件框架，则需要对新版LibXR进行重新适配，并验证 USB、CAN、UART的稳定性。

后续的改进是将下位机的can映射到gs_usb而非原生socketcan。映射到gs_usb可以极大程度地降低开发和维护难度。

机械臂控制

本赛季机械臂控制仍然以位置控制框架为主，而非基于的力控框架。该方案在工程实现和调试稳定性上更容易落地，但在接触任务、力反馈控制和自动装配等场景下，控制能力仍存在一定限制。

同时，由于机械臂动力学参数不够准确，任务空间导纳控制在实际测试中出现了振荡问题，外力估计结果也存在较大噪声。本赛季本人曾尝试以 SolidWorks 导出的质量、质心和惯量参数作为初始值，并通过带约束的梯度下降方法拟合动力学参数，但最终效果并不理想。后续仍需要进一步研究更可靠的参数辨识方法。

USB2EveryThing 设计理念

USB2EveryThing 的初始设计目标，是通过 USB 将下位机外设映射为上位机的原生外设，使上位机能够以 SocketCAN 和 tty 字符设备的方式统一访问 CAN 与 UART 设备。该设计在软件抽象和上位机开发便利性上具有明显优势，但在高频传感器的接入中仍存在局限。

在延迟测试中，仅USB2CAN的 P50 回环延迟就已经达到461.237us。如果进一步将 I2C、SPI也映射到上位机，并在上位机中完成连接在 I2C/SPI 上的 IMU 姿态解算，由于 IMU 反馈频率较高，导致延迟难以控制，同时也会让时间戳不可信。

受经费和硬件条件限制，现有USB2EveryThing 设备采用的MCU为 STM32G0B1CBT6，其内核为 Cortex-M0+，且无硬件 FPU，难以承担高频率姿态解算任务。因此，当前方案也无法将 IMU 作为一个已经在下位机完成姿态解算的独立字符设备直接映射给上位机读取。

后续改进是对C板进行兼容，在C板上进行imu姿态解算，再将imu姿态结算单独映射为一个tty字符设备到上位机。
