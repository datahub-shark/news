1、前言

   笔者是 Aurora 2026 赛季的英雄电控。队内直到今年二月才正式敲定由我一人着手开发自定义客户端，而当时英雄整车的进度也比较紧张，因此我没有充足时间系统学习一遍桌面客户端、前端、后端、视频处理和网络通信所涉及的完整软件开发流程。

   项目中的前后端代码有相当大一部分是在 AI Agent 工具辅助下完成的。我主要负责确定需求、选择技术路线、拆分问题，并结合代码审查、仿真和实机联调不断修正结果。AI 确实显著降低了跨技术栈开发的门槛，但它并不能替代对协议、数据流、异常恢复和实战需求的判断，这一点在项目后期尤其明显。

   目前客户端只在 Debian 13 上完成了较完整的开发和运行验证。Ubuntu 24 及更新版本理论上具备相近的依赖环境，但我没有进行完整测试；Fedora 则在实际尝试中暂时未能顺利跑通。项目也没有经过广泛的硬件兼容性测试，更没有针对低配置电脑做系统性的内存和性能优化。坦率地说，我对当前的完成度和测试覆盖并不满意，还请各位大佬多多包涵。本项目想要起到一个抛砖引玉的作用，**社区中已经有比较多的优秀的自定义客户端项目和技术文章。**

   赛季初期，队内对自定义客户端的热情并不高。我们最先关注的是比赛信息获取，而官方客户端与官方硬件已经能够很好地满足基本操作需求。基于这种先入为主的认识，自定义客户端对当时的队伍而言作用很小，甚至可以说没有明确的战术价值。

   最初完成基础 Demo 后，我本来准备就此收尾。后来，五大湖联合大学开源的英雄低码率吊射上位机方案，为我们当前的吊射画面痛点提供了一条很有价值的解决思路：额外部署一台相机，将压缩后的低码率画面通过机器人自定义数据链路送回操作手电脑。这样，即使官方图传在吃镖、遮挡或链路波动时出现黑屏，操作手仍有机会从另一视角获得画面。

   需求因此发生了变化。这个客户端不再以“重新做一个官方客户端”为目标，而是以英雄的双路图传和必要信息展示为核心。开发早期我确实设想过用自定义客户端完全代替官方客户端，但随着对比赛和操作手需求理解加深，我逐渐意识到，官方硬件与官方客户端在稳定性、交互成熟度和实战验证方面都更可靠。就目前而言，我们的自定义客户但仍不能取代官方客户端，它更适合作为补充画面和信息的第二终端。

2、技术选型与整体架构

   客户端采用 Wails 构建桌面程序：Go 负责 MQTT、UDP、协议解析、视频重组和原生播放器管理，Vue 3、TypeScript 与 Pinia 负责透明 HUD、配置和交互。视频解码没有放进 WebView，而是交给独立的 ffplay 进程；Wails 窗口只负责绘制透明 HUD，再通过 X11/XWayland 窗口层级把视频压在 HUD 下方。

3、项目特色

1. 组件化、可编辑的 HUD

   前端采用组件形式组织 HUD，各个组件可以自由拖拽和调整布局，也可以根据操作手的需求选择隐藏或显示。最初决定使用组件化设计，主要是考虑到它的可扩展性较高：后续可以结合官方提供的各种自定义客户端指令，继续增加新的信息组件，而不需要重新设计整个界面。

   项目初期，我对自定义客户端的认识还不够深入，一度希望用它完全代替官方客户端。随着开发和实际使用逐渐推进，我发现赛事官方提供的硬件和官方客户端，无论是成熟度还是操作体验，都比当前由我们自己设计的客户端更适合操作手，因此后来也重新规划了自定义客户端在队内的战术定位。

   就目前而言，我们的自定义客户端仍然无法取代官方客户端，主要用途还是传输额外画面，在英雄吃镖导致官方画面黑屏时提供一条补充视角。虽然项目目标发生了变化，但组件化形式仍然为后续扩展保留了便利：不同兵种或不同操作手可以按自己的需要选择信息，而不必被固定布局限制。


2. 官方图传与自定义图传画中画

   英雄操作手需要同时关注官方 H.265 图传和通过 0x0310 回传的自定义 H.264 画面，因此客户端专门设计了主画面与 PiP 小窗。两路数据都有效时，各自拥有独立播放器；切换视频源时主要交换主画面与小窗的几何位置和堆叠关系，正常情况下不需要为了切换而重新建立整条解码链路。按下 F 或在设置面板中选择视频源即可切换。

   官方链路监听本机 UDP 3334 端口，接收比赛服务器发来的 H.265 分片；自定义链路则从 MQTT 的 CustomByteBlock 消息中取得机器人端 0x0310 上传的字节块，再还原为 H.264 访问单元。PiP 并不是一张定时刷新的缩略图，而是持续接收帧的真实视频窗口，因此操作手能够同时观察两路画面的连贯性和延迟状态。

3. 视频不进入 WebView

   如果直接在 WebView 中解码和合成视频，浏览器媒体管线会带来额外缓冲，而且透明 HUD 与视频的合成也更难稳定控制。Aurora Client 因此让 ffplay 负责解码与渲染，WebView 只绘制 HUD。后端根据 HUD 顶层窗口的位置和尺寸，持续校正两个视频窗口的几何与层级关系，使其满足“HUD 在最上层、PiP 位于主画面之上”的顺序。

   Linux 桌面环境下，真正找到 ffplay 窗口并不只是按标题搜索这么简单。实现中会综合进程 PID、窗口标题、窗口类名和几何信息逐级回退，并递归查找 XWayland 下的子窗口。多屏切换或窗口重新映射后，后台也会重新读取几何位置并进行校正。这部分实现较依赖 X11/XWayland，也是当前跨平台能力受限的主要原因之一。

4. 面向断流的重组与恢复

   低延迟视频最怕的不是偶尔丢帧，而是丢帧后持续积压，最后操作手看到几秒前的画面。因此播放器前只保留很小的帧队列，策略是“保留最新、丢弃旧帧”，过期帧也不会继续送入解码器。这里宁愿牺牲一部分连续性，也不希望延迟无限累积。

   官方 H.265 链路在起播或播放器重建后，会等待 VPS、SPS、PPS 与可恢复关键帧齐全再放行，避免 ffplay 从预测帧中途启动后立即退出。自定义 H.264 链路收到的是连续的 300 字节块，本身没有完整帧边界，因此客户端需要识别 NAL 起始码、缓存 SPS/PPS，并解析切片信息来判断访问单元边界。中途接入或长时间断流后，重组器会重新等待可恢复的 IDR，而不是把残缺数据直接交给播放器。

   播放器管道写入失败或进程异常退出时，后端会回收旧进程、重置对应同步状态，并等待下一组能够重新解码的数据。链路诊断卡同时展示官方/自定义源是否在线、当前显示角色、最近数据延迟和丢弃情况，便于区分“没有收到包”“收到包但未等到关键帧”和“播放器窗口未成功建立”等不同问题。

    赛事自定义上传链路按 300 字节、最高 50 Hz 传输，理论数据量约为 15 KB/s，因此它并不适合追求高清画质。上位机必须把码率压到链路能够长期承受的范围，客户端也必须假设数据块可能丢失、重复或从任意位置开始。这个画面的价值不在于替代官方高清图传，而在于提供另一个视角和一条独立的恢复路径。

   当前方案让云台 C 板承担 USB 接收、缓存、分包和转发，优点是可以复用现有图传链路，英雄的遥控器控制也是直接通过图传接收端控制的，代价则是占用本就紧张的单片机内存。更合理的方案可能是由上位机直接完成协议封装并连接图传模块，让 C 板继续专注实时控制。仓库中的架构说明保留了这部分取舍，方便后来者根据自己的硬件条件重新选择。

5、运行环境与适用边界

   面向 Linux，完整运行需要 Go、Node.js、Wails、WebKitGTK、GTK3 与包含 ffplay 的 FFmpeg。开发环境使用 Go 1.25 及 Node.js 20.19 以上版本。

需要再次强调以下边界：

•Debian 13 是目前唯一完整验证的平台；Ubuntu 24 及以上仅属于合理预期，Fedora 暂未跑通。

•原生视频层依赖 X11/XWayland 的窗口能力，纯 Wayland 和其他操作系统尚未形成可靠方案。

•没有针对低配置终端做专门的内存、启动速度和功耗优化。

•没有进行足够广泛的比赛环境、硬件组合和长时间稳定性测试。

•多兵种身份与遥测已经接入，但 0x0310 自定义视频当前服务于英雄链路。


   以上部分限制也正是我目前对整个项目完成度仍不满意的主要原因。将这些问题明确写出来，并不是为了回避项目中仍然存在的不足，而是希望后来使用或二次开发的同学能够正确判断它目前所处的阶段：代码已经具备可运行的基础，但“能够运行”并不等于“可以不经验证直接上场”。 本项目按当前状态开源，可供学习、交流和二次开发参考，但不对特定操作系统、硬件配置或比赛环境下的稳定性、实时性和可用性作出保证。仅仅起到抛砖引玉的作用，绝大多数人做的比我要好。

8、后记

   正如前文所说，我没有充足的时间系统学习桌面客户端、前端、后端、视频处理和网络通信所涉及的完整软件开发流程。我很清楚，对于一个希望真正投入比赛的工程而言，仅仅把功能实现出来远远不够；如果没有充分理解整条链路，也没有完成系统性的验证，这样的开发过程就谈不上完善和负责。AI Agent 帮助我在短时间内跨过了多个陌生技术栈，但生成代码并不等于完成工程。因此，我更希望这个项目只作为一个可以继续讨论和改进的起点，起到抛砖引玉的作用。对于已经实现的内容，我也尽我所能补充说明、架构文档和使用边界，希望后来者至少能够看懂它为什么这样设计，又有哪些问题尚未解决。

   更遗憾的是，赛季后期我们发现英雄本身仍存在一些技术问题，最终无法稳定完成从高台吊射命中敌方基地。这个战术前提一旦不成立，围绕吊射辅助画面构建的自定义客户端也就失去了最初的实战落点，没有机会按照预想进入完整的比赛流程。

   与此同时，我对五大湖联合大学开源方案的复现也并不完整。例如，原方案中的局部保彩图像处理效果没有被完全实现，相机的放大倍率也可能不足。队内当时能够使用的最长焦距镜头只有 8mm，对于远距离基地画面的辨识能力很难达到理想状态。这些看似属于图像端或硬件端的问题，最终都会直接影响客户端收到的画面是否真正具有战术价值。

   因此，从严格意义上说，这个项目没有经历真正的赛场实战检验，也没有完成它最初预定的任务。现在开源的更像是一套缺少最终实战闭环的原型，而不是一套经过比赛充分验证的成熟方案。这也是我在前文反复说明项目边界并保留免责声明的原因。

   遗憾总是存在，但在队伍中的这一年依然给我带来了很多成长。我认识了许多朋友，也继续对RM这个赛事氛围痴迷，也接触了过去完全陌生的技术和工程问题。

   出于个人规划和其他多方面原因，作为正式队员仅一年的我选择离队。这篇文章以及对几个仓库文档的整理，也算是我为这段经历留下的一份阶段性总结和交接。项目没有按照最初设想完成实战落地，并不意味着其中的尝试毫无意义。如果这里记录的某种方案、某个错误或某次取舍，能够让后来者少走一点弯路，或者启发社区做出更简单、更稳定、更适合实战的方案，那么这次开源就已经有了价值。
