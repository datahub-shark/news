青岛大学 面向全兵种的模块化跨平台机器人软件框架开源

Nguồn: RoboMaster BBS · Tác giả: 摆烂电控.

Chuyên mục: Khác

摘要

针对 RoboMaster 机器人开发中平台接口差异、跨兵种代码重复及团队技术传承等问题，青岛大学未来战队基于 LibXR[1] 与 XRobot 工具链，构建了一套面向多兵种协同研发的模块化机器人软件框架。框架通过硬件与系统抽象隔离平台差异，以独立模块仓库组织业务功能，并利用 YAML 配置描述模块依赖、实例参数及组合关系，生成项目入口代码。在此基础上，形成了覆盖嵌入式电控、Linux 自瞄与 Webots 仿真的统一工程组织方式，并引入模块构建检查、车型配置矩阵构建和固件归档流程。

本次开源重点介绍该框架的设计动机、模块组织方法及工程实践，为参赛队伍开展跨平台开发、模块复用和长期维护提供参考。“面向全兵种”描述框架的设计范围；具体可用功能与部署条件，以各仓库当前发布的实现、配置和文档为准。

一、工程背景与设计目标

RoboMaster 机器人系统通常同时包含电机控制、姿态估计、通信、视觉感知及任务控制等功能。不同兵种在执行机构、控制参数和任务逻辑上存在差异，但又共享大量底层驱动与通用算法。随着功能积累和人员更替，如何在满足实时控制需求的同时维持代码的可复用性与可维护性，成为战队软件工程中的长期问题。

在本赛季重构之前，未来战队已经形成了一套基于早期 XRobot 架构的机器人代码。原有工程具备较完整的功能，但随着业务扩展，也逐渐暴露出两类问题：其一，大量业务代码与多项依赖集中于同一仓库，工程初始化、依赖获取和环境配置较为繁重；其二，以整车或兵种为单位维护代码，容易使通用功能与车型差异相互交织，增加跨兵种同步修改和接口协作的成本。

因此，本次重构将重点放在三个方面：通过统一接口缩小平台适配对业务代码的影响；通过独立模块与显式配置分离通用功能和车型差异；通过自动化构建与文档规范，使技术成果能够在不同成员、不同机器人及后续赛季之间持续复用。

在刘骢学长的指导与帮助下，团队从赛季初开始迁移既有功能，逐步完成通信链路、电机控制、上下位机交互等基础能力的整合，并在集中备赛期间持续调整业务模块与配置结构。这一过程也推动团队的协作单位由整车工程逐步转向可独立维护的功能模块。

二、总体架构与职责划分

本框架采用分层组织方式，将平台适配、通用运行时、业务模块和项目配置分别管理。LibXR、XRobot 与战队业务仓库承担不同职责，三者共同构成从底层接口到整车应用的开发体系。[1–3]


层次主要组成职责
平台与板级适配芯片 SDK、操作系统、BSP、仿真设备接口完成外设初始化、系统接入及设备映射
通用运行时LibXR提供硬件抽象、线程与同步机制、消息与事件等基础能力
功能模块电机、底盘、云台、通信、视觉等独立仓库封装设备功能、控制算法和业务逻辑
项目配置与工具链XRobot、YAML 配置、代码生成工具管理模块来源与依赖，描述实例参数并生成项目入口
构建与交付CMake、容器环境、GitHub Actions执行构建检查，归档配置和固件产物

LibXR 由刘骢学长主导设计，为本框架提供跨平台运行基础。其价值在于将硬件访问和系统服务组织为相对一致的接口，使业务模块能够围绕功能语义编写。XRobot 则负责模块仓库管理、配置处理和入口代码生成，减少项目组装过程中的重复劳动。QDU-Robomaster 组织中的仓库承载面向赛事需求的具体实现与集成配置。

2.1 硬件抽象与平台适配

在 STM32 工程中，配套工具可解析 STM32CubeMX 的 .ioc 配置，辅助生成 LibXR 的板级适配与初始化代码。BSP 将外设对象注册到 HardwareContainer，业务模块通过约定的名称与类型获取接口，从而减少对具体芯片外设编号和厂商 API 的直接依赖。

这一机制使“使用某一路 CAN 接口”与“该接口在具体芯片上如何初始化”能够分别维护。迁移平台时，开发者主要处理目标平台驱动、设备名称映射及系统配置；在所需接口和运行条件得到满足的前提下，业务模块可以保持较高程度的源码复用。

LibXR 当前源码包含 STM32、CH32、ESP32、HPM、MSPM0、Linux 和 Webots 等驱动目录，并提供裸机、FreeRTOS、ThreadX、Linux 等系统适配。不同平台及芯片系列的外设支持程度并不相同，应结合上游支持列表与具体驱动实现选择目标平台。[1]

跨平台能力也有明确的适用条件：模块应尽量依赖 LibXR 接口，避免直接包含芯片专属头文件或调用厂商 HAL；同时仍需检查外设能力、线程调度、执行周期及资源占用。统一 API 为移植提供基础，实际控制性能仍需在目标硬件上验证。

2.2 模块通信与业务解耦

框架通过 Topic 消息组织数据交换，并通过事件表达模式切换等离散行为。例如，底盘模块订阅控制命令、裁判系统功率信息及云台状态，在模块内部完成控制计算；事件联动则可由 EventBinder 集中描述，将源模块事件映射到目标模块事件。[3,5]

这种组织方式将数据处理、控制算法与模块联动关系分别表达。开发者可以在接口兼容的前提下替换具体实现，也更容易追踪一条控制指令从输入、状态转换到执行机构输出的路径。

三、基于 YAML 的模块组装与协作机制

本次架构迭代的关键工程改进，是将可复用的模块实现与面向具体机器人的组装配置分离。仓库组织和实例配置主要涉及以下文件：[2]


文件描述内容
Modules/sources.yaml模块来源索引
Modules/modules.yaml项目所需模块仓库及版本引用
User/xrobot.yaml 或车型配置文件模块实例、构造参数、模板参数与实例引用关系
User/xrobot_main.hpp由配置生成的项目入口代码

YAML 在这里承担构建前的配置描述角色。XRobot 根据模块清单和实例参数生成 C++ 入口代码，再由编译工具链完成类型检查与链接。这使配置具备可读性和可审查性，也避免为模块组装额外引入运行时配置解释流程。

以电机模块为例，同一实现可以通过多个实例分别服务于底盘和云台，设备 ID、方向、总线名称及控制参数由具体配置给出。对于不同兵种，共享能力由模块维护，机构差异和设备分配则保留在车型配置中。Chassis 模块也通过模板参数选择全向、麦克纳姆或舵轮等底盘实现，为同类功能的复用提供统一入口。[4,5]

由此，团队可以按功能分配开发任务：模块维护者负责接口、实现和模块级检查，整车集成者负责模块组合、设备映射与系统联调。通用功能的修复可以通过模块版本更新复用于多个工程，减少在不同车型代码间手工复制修改的需求。

多仓库组织也带来了依赖版本协调问题。复现某一固件时，需要同时记录 BSP、LibXR、模块仓库及生成工具的版本；仅保存 YAML 文件，而依赖持续变化的分支，仍不足以重建完全相同的软件状态。为了解决这一问题，我们提出了CI/CD流程，每当上传一次车辆描述.yaml我们会进行一次全量CI检查，当全流程通过会发布一版固件留存下来，理论上只要你认真写commit描述就能够快速定位到某一准确的历史版本

四、公开实现与典型应用

4.1 多兵种电控组织

QDU-Robomaster 组织已公开多类设备与业务模块，包括电机、遥控、姿态传感器、底盘、云台、发射机构、裁判系统、功率管理及上下位机通信等。具体实现可在 RMMotor、DMMotor、DR16、BMI088、Chassis、Gimbal、Referee、PowerControl、HostData 等仓库中查阅。

4.2 Linux 自瞄与 Webots 仿真

自瞄系统分别提供 Linux 实物工程和 Webots 仿真工程，核心处理过程围绕相机与姿态同步、装甲板检测、目标跟踪、瞄准解算和控制输出展开。[3,6]

相机图像与姿态数据        ↓    数据同步        ↓ ArmorDetector        ↓ ArmorTracker        ↓      Aimer        ↓实机控制输出 / Webots 云台与发射接口

实物工程接入真实相机、IMU 和上下位机通信；仿真工程使用 WebotsCamera、WebotsGimbal、WebotsFireNotify 等模块连接虚拟设备。二者沿用共同的模块接口和配置方式，使检测、跟踪与瞄准等业务环节能够在不同运行环境中集成。

这种设计为算法调试和系统联调提供了较低的硬件依赖，也便于在可重复的场景中观察数据流和控制输出。仿真与实机之间仍存在成像特性、通信延迟、执行器动力学及噪声等差异，因此仿真中的功能验证需要与实机标定、时序检查和命中效果测试相结合。

五、持续集成与固件交付

独立模块仓库使构建检查可以在功能边界内开展。以 EventBinder 为例，其 GitHub Actions 工作流使用预配置的 Linux 容器环境，获取依赖、生成入口并执行编译；Linux 自瞄工程则对多份运行配置依次生成和构建。[7]

在整车集成层，bsp-dev-c 通过车型配置矩阵分别构建固件，并将 .elf、.hex、.bin 文件与对应 YAML 配置一并归档；工作流还配置了在版本标签或 Release 事件下上传发布附件的流程。[7] 将配置与固件共同保存，有助于识别部署对象，并为备赛期间取回既有版本提供基础。

这些流程分别检查模块能否集成、配置能否生成以及目标工程能否构建。Linux 构建可以暴露部分平台专属依赖，车型矩阵可以发现配置与接口不一致的问题，但它们并不能单独证明所有平台兼容，也不能替代控制闭环、通信可靠性和整车运行测试。比赛中使用的稳定版本仍应与具体硬件和已完成的实机验收相对应。

六、工程价值与后续工作

这套框架的工程价值主要体现在三个方面：统一接口使平台迁移工作更集中于适配层；模块与配置分离使跨兵种复用和团队协作具有更清晰的边界；从模块构建到车型固件归档的流程，使软件交付具备更明确的检查入口与追踪依据。

对于人员周期性更替的学生团队，架构的长期价值还体现在知识组织方式上。将接口语义、配置约定、构建入口和调试方法沉淀到模块及文档中，有助于后续成员理解已有设计，减少因维护经验流失而重复重构的成本。
