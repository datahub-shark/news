RC2026 哈工深南工问天战队 面向 STM32 平台的团队协作与代码复用方案及本赛季可复用驱动库开源

Nguồn: RoboMaster BBS · Tác giả: syhanjin

Chuyên mục: Điều khiển

在 STM32 嵌入式平台上开发控制算法时，真正消耗团队时间的往往不只是算法本身，还包括代码移植、接口适配、工程重构和后续维护。

同一种算法可能被不同成员重复实现，代码风格和接口各不相同；当一个人想复用另一个人的底层逻辑时，又必须先适配原项目的目录结构、任务模型和调用方式；复用后的代码经过修改，也很难顺利回馈到原项目。久而久之，团队会不断在“重新实现”和“迁移旧代码”之间循环，代码库也在下一次复用时重复产生同样的问题。

为解决这些问题，南工问天电控组在 2026 赛季逐步建立了一套搭载在 STM32 平台的工程结构、驱动库组织方式和包管理流程，并将最终成果开源于 HITSZ-WTRobot-Packages。项目采用 GPL-3.0 协议，目前仍在持续完善文档。

一、项目解决什么问题

这套方案的目标不是把所有算法写成一个庞大的代码仓库，而是建立一套稳定的协作边界：

  • 共享代码有清晰、统一的存放位置；
  • 不同类型的驱动和算法可以独立维护、独立更新；
  • 复用者不需要大规模迁移原作者的工程结构；
  • 发现问题或产生改进时，可以直接回到共享仓库修复并提交 Pull Request；
  • CubeMX 负责硬件配置和底层代码生成，用户代码与共享代码不被生成结果反复干扰。

项目的典型使用案例是 26-v2-r2-ind-mcu-chassis。

二、整体工程结构

项目基于 C++、CMake、Git、Git Submodule、FreeRTOS（CMSIS v2 封装）以及 STM32CubeMX 的代码生成功能搭建。

1. 共享代码统一放在 Modules

所有共享代码都放在项目的 ./Modules 目录下，并按功能类别拆分为独立 Repo。每个 Repo 作为 Git Submodule 引入项目。当前共有六个主要驱动库：

  • BasicComponents：基础框架、简单算法和常用小工具；
  • MotorDrivers：电机驱动库，目前支持 DJI、DM、VESC，并内置速度环和位置环 PID；
  • Sensors：传感器库；
  • VelocityProfile：速度轨迹规划库，目前支持 S 曲线单轴规划；
  • TrajectoryControl：单轴轨迹跟随库，支持多电机同步跟随；
  • ChassisController：适配多种底盘的底盘控制库。

这些仓库可以随着后续需求继续扩展，仓库内部也可以按模块增加实现。每个仓库中的小模块由配套包管理器 cpkg 管理，同时保留手动导入的方式。

Git Submodule 带来的直接收益是维护路径清晰：任何成员发现问题或有新的实现思路，都可以在对应驱动库中修复、提交，或者发起 Pull Request，而不必先把修改复制回某个具体比赛项目。

2. 用户代码与 CubeMX 生成代码分离

用户编写的代码全部放在 ./UserCode 下，不修改 CubeMX 生成的 Core 目录代码。这样可以将生成代码从 Git 追踪中排除，避免板上外设配置变化带来大量无关 diff；硬件外设信息由 .ioc 文件保存，项目被 clone 后再通过 CubeMX 重新生成底层代码。

这一约束会带来“不能直接修改 Core 代码”的副作用，项目通过 CubeMX 自身提供的扩展点解决：

  • 在 CubeMX 的 FreeRTOS 配置界面创建入口函数为 Init、优先级为 osPriorityRealtime7、代码生成选项为 As external 的 task，作为项目初始化入口；建议栈大小为 1024 words，其余 task 由初始化 task 创建；
  • 通过 ProjectManager -> Advanced Settings 右侧的 RegisterCallback，为具体外设注册回调函数，将回调逻辑从生成代码中分离出来，并避免默认 TIM 回调被 HAL 占用。

三、cpkg：为驱动库处理依赖

当驱动库被拆分为许多可复用的“包”后，手动导入每个包及其依赖链很快会变得不可维护。为此，项目配套开发了基于 Rust 的包管理器 cpkg。

cpkg 将包含 cpkg.toml 的目录识别为一个包。cpkg.toml 描述包名称、包名、版本、依赖关系和附加编译选项。常用操作包括：

  • cpkg package create：创建包；
  • cpkg package generate：根据 cpkg.toml 生成对应的 CMakeLists.txt；
  • cpkg sync：更新受管理项目中的驱动库；
  • cpkg add -I：通过交互式命令行选择当前项目依赖。

cpkg 通过 index 获取全部包信息，索引由 GitHub CI 自动更新。包含 wtrproject.toml 的目录会被识别为受管理的 STM32 项目。

目前，为兼容仍有手动导入需求的场景，生成的 CMakeLists.txt 暂时也纳入 Git 提交范围，未来版本预计移除这一要求。具体命令参数和完整使用流程以 cpkg 使用文档 为准。

四、代表性实现：

1. MotorDrivers

MotorDrivers 的目标，是为不同电机电调提供统一的上层抽象。更换电机时，上层控制逻辑尽量不需要重写，只需替换传入的电机类。

在 motor_if.hpp 中，驱动库提供 IMotor 和 IController 两个基类作为设计接口。这里的 IMotor 抽象对象是电调，而不是电机本体。它提供以下能力：

  • 反馈：getAngle、getVelocity、resetAngle；
  • 控制：setCurrent（或 setTorque）、setVelocity、setPosition、setMIT；
  • 状态检测：isConnected；
  • 控制权管理：tryAcquireController、releaseController。

其中，setCurrent 对应 DJI 电机协议，setVelocity、setPosition 和 setMIT 对应 DM 电机协议。

为了适配不同电机和不同控制链，Controller 提供统一的 ControlMode：

enum class ControlMode
{
    Default,        ///< 使用电机驱动声明的默认控制模式
    ExternalPID,    ///< 外部控制器计算输出，再通过 setCurrent() 下发
    InternalVel,    ///< 使用驱动器内部速度环
    InternalPos,    ///< 仅支持发送位置指令，不支持发送速度指令
    InternalVelPos, ///< 同时支持发送速度指令与位置指令
    InternalMIT,    ///< 使用 MIT 格式一并发送位置、速度、刚度、阻尼和前馈
};

这套接口将电调协议、控制模式和上层算法解耦，为后续替换具体电机、切换内外部控制环提供了统一入口。完整设计以项目文档为准。

2. ChassisController

ChassisController 通过 GPL-3.0 协议开源，目标是为底盘提供统一抽象，使不同底盘能够依赖同一套控制设计。

考虑到项目可能使用多种定位手段，ChassisController 将底盘控制拆分为定位、解算、控制三个部分。

定位：ILoc

定位部分继承自 ILoc，目前支持 JustEncoder 和 EKF。其中 EKF 使用编码器、陀螺仪和雷达进行融合定位；实现中包含先计算延时并进行反演、再进行 lidar 观测并正推融合的处理思路。

定位模块提供 velocity in body/world、posture in world 等状态能力，以及坐标转换辅助函数。相关实现可参考 ChassisController 的文档和源码。

解算：IMotion

解算部分继承自 IMotion，目前支持四轮麦轮、全向轮和舵轮。在 r2-chassis 中，还通过自定义方式实现了 4-DOF 独立升降麦轮底盘。

基类要求实现使能与失能判定、准备状态判定，以及受保护的 applyVelocity 作为控制量输入。准备状态判定允许 motion 进行独立自检，IMotion 同样提供控制权限制。

控制：IController

控制部分继承自 IController，目前包括两类逻辑：

  • 主机控制：导航在 MCU 上，Master 提供 7 种控制组合；
  • 从机控制：导航来自写入 Flash 的固定轨迹，或来自上位机的轨迹点。

这套设计已经提供完整文档，并应用于 2026 RC 的 R1 和 R2 底盘。

五、stm32tool：降低新项目启动成本

为了进一步降低项目上手难度，团队开发了 stm32tool，采用 MIT 协议开源。

stm32tool 可以快速构建一个受 cpkg 管理的 wtrproject STM32 项目。目前暂时支持 STM32F407VET6 和 STM32H723VET6。它的定位不是替代 CubeMX，而是减少新项目初始化、工程目录搭建和包管理接入的重复工作。

六、2026 赛季实践

这套项目结构在 2026 赛季被南工问天电控组全面使用。经过一个赛季的开发，团队完成了覆盖本赛季比赛大部分需求的驱动库，六大驱动库的具体实现均可在组织仓库 WTRobot 中查看。

七、当前不足与后续计划

项目目前仍存在明显不足，主要包括：

  1. 上手难度较高。截止目前，队内尚无其他电控成员能够完整理解驱动库的全部设计；不使用自动化工具时，新手初次上手可能需要数小时。
  2. 控制链传递关系尚未规范，仍可能出现多个上级同时控制同一下级的情况；同时，越过上级控制下级也较为困难。
  3. 控制算法仍有较大提升空间。由于往年可继承资料较少，当前实现中的部分控制算法相对基础。
  4. GitHub 访问限制会变相提高使用难度。项目虽然设计了 mirror，但主要开发仍在 GitHub 上进行。
  5. 项目尚未在 H7 系列芯片上实际使用，今年团队没有采用 H7 作为主控。

后续计划包括：

  1. 进一步完善自动化工具，降低上手成本；
  2. 重构并设计统一的控制器继承关系和控制权逻辑；
  3. 将与其他队伍交流得到的控制经验融入驱动库；
  4. 适配 H7，确保同时兼容 bxCAN 和 CAN FD；
  5. 扩大开源范围，邀请其他队伍成员参与开发和使用。

八、项目入口与适用场景

项目支持在 VSCode、CLion 以及其他 IDE 上开发，Keil 除外。对于正在使用 STM32、CubeMX、FreeRTOS 和 CMake 的机器人团队，这套方案可以作为 Git 工作流、驱动库拆分、控制接口抽象和多人协作工程结构的参考。

项目当前仍处于文档完善阶段，使用前建议先阅读各驱动库文档，再结合典型用例理解 Modules、UserCode、CubeMX .ioc 工程和 cpkg 之间的关系。

相关入口：

  • 驱动库组织：HITSZ-WTRobot-Packages
  • 包管理器：cpkg
  • 包索引：index
  • STM32 工程工具：stm32tool
  • 典型用例：26-v2-r2-ind-mcu-chassis

这套项目并不试图宣称控制算法已经完美，也不回避工程结构仍需继续演进的事实。它更重要的价值，在于把一个赛季中反复遇到的代码复用、依赖管理、CubeMX 生成和团队协作问题，沉淀为一套可以被其他队伍参考和继续改进的开源实践。
