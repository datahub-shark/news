机器人项目设计流程

   本文并非针对特定技术点的技术文档，而是一篇探讨适合RM机械小白的机械设计流程方法论的综合性论述。旨在系统阐述机械设计全流程的核心环节、关键决策点及测试验证的方法，为各位优秀的机械工程师和项目管理者提供一套结构化的设计管理框架。

   比起力求普适性，覆盖从简单零件到复杂系统的教科书。RM机器人的开发有着鲜明的特点追求轻量化、高频对抗性、严格的规则约束（尺寸、重量）、极短的迭代周期等。教科书上通用的设计流程无法聚焦这些核心矛盾。

   教科书侧重于工业场景的设计和规范，缺乏对RM这种资源紧张、时间紧迫，以及充满战术策略的机器人实战环境下的工况考量。无法通过教科书的内容进行取舍和权衡利弊。

   教科书上的标准/经验参数多基于理论计算和标准测试。RM赛场的工况要求机器人有更高的抗击打能力、稳定性、操控性以及战术适配性。有着属于自己的一套从方案提出-设计-测试-迭代的闭环过程。

   因此，本文将针对RM竞技机器人的开发提出一套流程方法论。

   聚焦于RM核心痛点：

•如何平衡“创新”与“可靠性”？ 新赛季需要新技术，但失败成本极高。

•如何在“极短周期”内完成“可靠迭代”？ 从规则发布到首场比赛往往只有数月。

•如何管理“高度不确定性”？ 其它战队、比赛规则、机器人技术都在快速变化和进步。

•如何实现“跨学科高效协同”？ 机械、算法、视觉团队如何无缝对接？

   将设计流程拆解为：

1.需求分析

2.方案调研

3.结构设计与仿真校核

4.测试验证

5.迭代优化

逐一进行介绍。

   作者想做的只有一件事：摒弃大型工业流程中繁重的文档和冗长规范，提供适合学生团队执行的、最小必要流程。但由于本人能力有限，本文内容基于课程学习及参加RM比赛以来的个人理解，内容并一定能涵盖RM机器人设计的所有内容，还请多多谅解。

零）设计流程


因为机械设计工作是一项创造性劳动，在设计之初许多问题和矛盾尚未暴露，因而上述的设计过程并不是一帆风顺的，也不会一次就能按部就班进行到底，而是不断反复和交叉，这是在设计中经常会遇到的正常现象。——机械原理（第九版） (孙桓,葛文杰)

    对于任何机器人设计项目，即使存在设计难度或者繁简程度不同，也都会经过如图中的几个阶段：1）模块划分；2）需求分析；3）方案调研；4）详细结构设计与仿真校核；5）测试验证；6）迭代优化。这个过程并非是一个连续性的、单调的过程，而是一个弹性的、交叉的过程。我在进行方案调研的阶段可能还会回到需求分析阶段，重新审视原定的各级需求并进行模块划分。我在进行测试验证的时候，也可能会因为测试结果返回方案调研阶段，重新选择一个更优的更合适的方案。

    在设计过程中的每个阶段都需要书写相应的设计文档或者测试文档，保障项目成功。

    接下来将开始对机器人项目设计流程的介绍。

一）需求分析

1.需求分析目的

既要又要，就是对自己的精神霸凌！

贪心需求，就是一次自杀式设计！

  1. 差分需求，化繁为简（剔除冗余、模糊、难实现的需求）
  2. 列举设计方案（原动机，传动装置，执行装置）
  3. 组合各个模块设计方案，明确具体框架

2.模块划分（机械层面）

模块划分的目的：

   模块划分的核心目标是将复杂的机械结构拆解成多个功能明确、可独立操作和更容易制造、组装和维护的部分。

模块划分的一般流程：

针对于一个已明确框架的机器人项目，一般可分到四个层级。

   第一层级按机器人的层次分，由上到下进行拆分，除明显的机器人层次之外的，电气元件、视觉系统、裁判系统可作为独立的层次划分出来，机械结构与这几个部分共同组成一台完整的机器人系统；

   第二层级按基本功能模块划分，将机器人进行功能性的拆解；

   第三层级按独立性划分，将各模块内部的独立子部分拆解出来；

   第四层级按机械机构划分，将各子部分所包含的子机械机构再次进行划分，这个子机械机构包含对应的原动机、传动装置、执行装置；

以华南虎战队24赛季国赛工程机器人为例：

   针对于一个全新的、未知框架的机器人项目，可以先进行需求分析、方案调研，等到该机器人项目的基本框架基本确定后在对机器人进行模块划分。

3.需求分析

3.1 需求收集

   通过规则手册确定机器人基本目标需求，提出拓展目标需求

   一般是用“必须达到的要求”，“至少到达的要求”，“希望达到的要求”予以确定。

基本目标需求：

    1. 定义：基本目标需求，即机器人完成任务所需要具备的最基本的功能或者说识别一台机器人所需要的关键特征。
    2. 来源：规则手册，如下图

拓展目标需求：

    1. 定义：在基本目标需求上提出更多的目标需求，可以是为了提高基本目标功能的性能而提出的需求或是满足其它可以提高机器人综合能力而提出的需求。
    2. 来源：分析、解读规则手册、比赛视频。

举个例子：一台步兵的基本目标需求就是底盘能动、能够发射17mm小弹丸。在此基础上又提出了发射散步8米100*100、二轴稳定云台（pitch角度-15°-30°、yaw360°）、弹仓容量500发、底盘能够通过45°坡等拓展目标需求。

3.2 需求理解

   通过比赛视频、开源文档或队员沟通理解最终应用场景和约束条件

应用场景和约束条件：

    1. 定义：即去探究所需要实现的这些需求背后所涉及的技术知识、可能面临的风险或者说是会产生的各种常规情况。
    2. 目的：理解该需求的能达到的实际效果、明确需要进行哪些技术知识的学习、进行难易度评估和风险评估。

举个例子：要实现发射17mm小弹丸，就需要去对发射机构类型的学习，以及基础的动力学理论的学习；

3.3 需求划分

   将需求细化到对应的功能模块和任务，并划分不同功能需求的重要性、难度和优先级

在理解需求后将每个需求与各模块相互对应，并且评估其重要性、优先级和难度。那么该如何去更好地评判/划分一个需求呢？在此给出一个可以参考借鉴的思路，要视具体情况而定。

    1. 基本目标需求均视为最重要，优先级最高，无论难易程度；
    2. 拓展目标需求中为原有功能上做的提升列为高优先级，根据实现的难易程度和重要性再进一步划分；
    3. 拓展目标需求中为附加功能/新增功能的列为低优先级，越难实现的优先级越低；

3.4 方案收集

   根据需求，通过头脑风暴、开源文档、比赛视频等，针对功能模块提出多种可能的设计方案

   这里需要说明/强调的一点是，需求和方案是不同的。需求是一个机器人要实现的目标，一个机器人要具备的能力。方案是一种方式，一种通过结构上的设计或是控制上的优化来实现既定目标（即需求）的方式。一个需求可以有多个方案，通过落实方案来保证机器人能够实现原定的需求，获得相应的能力。比如说，小陀螺，我们普遍都会说“这台机器人具备小陀螺的功能”，提到功能，大部分人都会认定为小陀螺应该作为“需求”来看待，但仔细思考一下，小陀螺的本质其实是利用导电滑环和相应的轴系设计来实现了机器人云台和底盘运动分离，底盘可以连续360°转动，其最终目的是为了躲避弹丸，提高存活能力。“小陀螺”，只是这种技术如今的普遍化使得我们将其视为了一台机器人必不可少的一项技术，但实际上小陀螺就只是一个为了解决“提高存活能力”的一种方式。所以在上述中，我们的需求应该是“更好躲避弹丸，提高存活能力”，而“小陀螺”是实现该需求的一种方案，完整的应该表述为“利用导电滑环和相应的轴系设计来实现了机器人云台和底盘运动分离”，除此之外的其它方案还会有“猫步”、“高低装甲板之类”等方案。

2.方案收集

方案收集：根据需求，通过头脑风暴、开源文档、比赛视频等，针对功能模块提出多种可能的设计方案。

2.1 收集渠道

  1. 官方论坛https://bbs.robomaster.com/article
  2. 开源文档
  3. 比赛视频
  4. 青工会视频
  5. 各大视频平台的开源视频、各大论坛（知乎等）、公众号等
  6. 机械结构设计图册等相关书籍
  7. 队伍交流，线上/线下
  8. 队内头脑风暴

2.2 方案类别

  1. 可以是只包括传动部分的方案；
  2. 可以是只包括执行部分的方案；
  3. 可以是只有一个动力源；
  4. 可以是一个完整机构（包含动力源、传动部分、执行部分）的方案；

3.方案评估

方案评估：利用低成本的方法评估各方案的可行性、成本、时间要求以及技术风险，选择最合适的方案

3.1 评估内容

  1. 可行性；
  2. 加工装配与制造成本；
  3. 时间成本；
  4. 技术风险；

3.2 评估方法

  1. 查阅开源报告；
  2. 与人交流；
  3. 原理性分析；
  4. 可行性分析：

   a.对照规则手册和制作规范；

   b.简单数值计算；

   c.简化模型进行仿真（sw草图仿真等）

什么是机械设计中的自上而下设计？

Top-Down（自上而下）的设计

所谓自上而下就是根据已有信息，设计出雏形方案，再以二维绘图的方式将方案表现出来，并设定符合要求的关键性参数，然后以这个复杂的二维图为基础，逐步完成各个子部件，这样做的好处就是控方案控制力强，不需要花费大量时间修改零件尺寸，修改机体只需要调整总控、分控的二维图，零件、装配体都会跟着随动。


Button-Up（自下而上）的设计

自下而上的方法主要是依据一些标准件或一些已知的零件形状，从零件开始设计，把零件装配起来，然后不断修改尺寸，以求达到要求

四、测试验证

1.测试的目的

  • 模拟赛场真实情况
  • 测车辆在赛场上的真实表现
  • 预见一些可能发生的问题
  • 确定测试条件、测试背景
  • 迭代到整车设计中，不断修改
  • ”量化一切可量化的“

最终目标：提高整车稳定性与性能

2.测试的类别

2.1 按测试目标来分

  • 功能测试：对所需要验证的功能进行测试，确定是否能够达到各级需求的目标，尤其是一级需求

实际意义：方案验证与功能确认

  • 性能测试：对可实现的功能的功能实现程度（能够达到多快的速度、多高的精度等，通过测试得出机构的实际上限）、稳定性（失误概率有多大、功能是否在一场内稳定实现）、易用性（功能实现是否简单易懂，动作组是否流畅稳定）、可用性（该功能是否随时可用、方便使用、效率多高）

实际意义：为操作手提供机器人基础数据，为战术组制定战术提供依据，可视化机器人战力

  • 强度测试：机构在实现基础功能时，在常规情况下，机构的质量有多”好“，逐步性地测试其刚强度、磨损量、疲劳性

实际意义：明确零部件使用寿命和应用场景，避免不正当操作造成资源浪费

2.2 按测试对象来分

  • 模块测试

   针对于单个模块的测试。特点是迭代快、效率高、维护代价

  • 整车测试

   涉及多个模块的联动测试。验证整个项目是否符合预期的需求和设计的要求

2.3 按测试的阶段来分

  • 单元测试

   即模块测试

  • 集成测试

   将一个个子模块进行联合测试，增殖式集成方式。如动作组测试

  • 系统测试

   确定测试的环境，与其它外部的元素结合在一起，在实际运行环境下对项目进行一系列的测试。比如某功能能否正常运行，软件在该实际环境下能否正常运行。如机器人大规模联合测试

  • 验收测试

   也称交付测试，以用户（操作手）为主的测试，由操作手参加设计测试用例，使用实际数据进行测试，确定项目是否满足验收标准，是否满足用户使用需求。

  • 回归测试

   在此前测试过程中出现问题，修改问题后，上车进行再次的测试，以确定是否达到预期需求。

3.测试的思路&流程

3.1 预测常见问题

  1. 在设计中我们会对自己部分结构设计不自信，可能会造成潜在问题，如：

 螺钉松动导致旋转副卡死

 板材断裂导致车体损坏

 悬挂收到冲击断裂

 这时就需要在后续步骤中提前关注这些项目，以防出事

2.对机器人功能、性能、强度的怀疑，可能达不到指标的问题，如：

 工作空间不够

 无法过隧道

 无法稳定下台阶

3.在赛场上会出现的常见风险，如：

 冲撞

 弹丸击打

3.2 列出关联因素（变量）

针对要测试的问题，列举出他的关联因素，在之后测试中着重关注这些部分，通过控制变量的方法来验证和解决问题，如：

3.3 确定测试项目

   确定测试项目的时候需要明确测试的目的，对点测试，针对可能出现的问题点进行测试，验证与解决问题；每个人负责的兵种和模块都不一样，需要测试的项目也不完全相同，但是其测试的思路都是一致的。以下测试项目仅作举例，实际情况以各自负责的模块为准。

  • 简单跑场测试（运动性能测试、盲道通过测试、各种坡度地形通过性测试、坡面运动测试、运动过程整车重心变化等等）
  • 运动强度测试（飞坡测试、35.5坡、下台阶测试）
  • 击打测试（小弹丸击打测试、大弹丸击打测试）
  • 漏弹测试（被两种弹丸击打后车体内存留多少弹丸）
  • 发射测试（大/小发射精度和卡弹测试）
  • 机构运动测试（pitch运动是否会干涉、舵结构是否会出现失灵、工程各机构多次运动是否正常）
目标一致：功能-性能-强度

3.4 确定测试流程

对于每一种项目都需要去确定对应的具体的测试流程：（每一种测试流程）

  1. 测试方案
  2. 测试次数

   a.量化测试结果

   b.功能测试从0开始，整体测试数量不多，保证需要能够验证正在测试的这项功能的可行性为止

  c.性能测试从最基础，最低的数据（数据来源为队伍往年的测试数据，其它队伍的数据，看比赛视频的得出数据，自己预估数据）开始，逐渐提高数值，直至达到机构的上限

  d.强度测试次数，计算公式=单局可能的运动次数 x 分区赛/国赛打满所有小局 x 安全系数（先取2，看实际测试量可以下放到1.4~1.5）

3.测试项目的优先级

   a.根据测试任务的难易程度，以及对整个项目的影响程度，为每条测试任务标注优先级。优先级高的测试任务需要优先测试，以保证整个测试工作顺利进行。

4.测试的具体实施方式+跟进人

   a.跟进人需要进行任务的沟通，让他们明白他们负责模块以及他们的重要性。

   b.跟进人需要是结构的负责人或者对该结构熟悉的人员

5.如何进行数据记录

   a.数据记录的规范会直接影响到你后续的数据读取和处理的便利性，你的数据记录要从问题出发，通过数据组尽可能总结出需要的问题

   b.进行视频拍摄，必要时拍摄慢动作视频（看看能不能自己搞到一台运动相机。）

   c.视频上传至统一存放站，做好命名和分组！！！

3.6 追源溯本与优化方向

   从原理出发，从现象来看，让问题根本无法出现，而不是让问题出现概率变小。

  1. 进行数据分析，作excel图表、多次观看视频、尝试复现问题，找到问题所在
  2. 针对识别到的问题进行根本原因分析，找出导致失效的关键因素。
  3. 提出针对性的设计优化建议，增强机构的适应性和可靠性。
  4. 输出测试文档（测试记录、测试总结、优化方案）

4.测试的注意事项

  • 必须严格走完测试流程，不得抱有”能用就行“、”差不多得了“等随便的态度；
  • 提前准备好测试所需的物资、场地、工具等；
  • 注重模拟真实的赛场情况，区分常规情况、特殊情况（非常规情况）、罕见情况（即极小概率事件）、不可能事件；
  • 不要”自我感动“，想清楚自己测试得到的数据是否是真实可信，是否能够得到想要的效果；
  • 出现问题时，一定要和队友同步信息，并且一起解决问题，而不是”这是你的问题，你马上改“，机器人是大家一起的，荣誉也是大家一起的，只有互相包容，共同承担，才能够解决问题；
  • 一定要记录，记录好次数、问题，留存一定数量的视频，没有记录的测试是没有意义的；
  • 谨记“墨菲定律”，会出错的，终会出错，永远不要抱有侥幸心理。发现有问题或可能出问题的地方一定要优化；
  • 测试时注意保护人身安全，机械臂工作范围、弹丸击打范围内测试时不要站人，人身安全高于机构安全 ；
  • 测试记录及时同步，效果最好的，出现问题的记录可以发到车组大群；
  • 多陪陪自己的队友一起测试，不懂多问，多学，多答；
  • 测试过程可能会很枯燥，坚持下去！

五、设计与优化文档规范

一份合格的设计文档需要包含哪些内容？

  1. 需求分析与模块划分
  2. 框架设计与尺寸确定
  3. 方案调研与确定过程
  4. 结构设计思路
  5. 零部件选型与校核过程
  6. 优化方向

   注意这是说的是“过程”，需要有始有终，有中间经历有最终结果，是你设计思路的体现，描述了你如何去解决一个问题，是确保正确完成工作最有用的工具，其目的是迫使你对设计展开缜密的思考，并收集他人的反馈，进而完善你的想法，同时在交接的过程中，能让其他人更通俗易懂的了解之前的设计目的和思路；

为什么要写设计文档？

   在设计流程的每个阶段强制输出文档（需求文档、方案报告、仿真分析书、测试记录等），绝非“形式主义”或“额外负担”，而是工程实践的智慧结晶，尤其在RM这类高动态、强协作、容错率低的竞技机器人开发中，文档是保障项目成功的关键。

  1. 目的是迫使自己对设计展开缜密的思考，并收集他人的反馈，进而完善自己的想法；
  2. 让其他人或自己更好的了解之前的设计目的和思路；
  3. 便于传承技术经验；
  4. 可能会有人这样觉得："设计文档没有用，是用来糊弄客户和管理层的文档"，”用来写设计文档的时间，我的任务早就做完了"”项目紧张，没有时间做设计"，这种说法是不正确的，对小的功能来说没毛病，但是大的复杂的任务时就很容易出现各种考虑不周、大量 BUG、甚至返工的情况，每个团队都应该根据自己的任务周期合理约定文档撰写的内容，什么情况该写什么。

写设计文档需要注意什么？

  1. 不是绞尽脑汁用一些高级的词汇或者话语去描述自己的设计，我们需要写的是这个设计怎么来的，为什么要这个设计，这个设计带来的影响有哪些？简言而之就是，去写清楚你的设计方案的原始需求是什么？选择这个方案/不选择其它方案的理由是什么？
  2. 该有的选型过程，计算过程，受力分析都应该要有；

3.一定要规范文档的命名，避免查阅困难，这也是个人态度的体现；

4.发现在设计过程中有存在自己不懂的技术点和新的知识，可以输出学习文档；

5.方案讨论的过程也可以放在设计文档里面；
