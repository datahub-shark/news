基于 MR300C 成品 WiFi 图传模块的低成本（约 300 块）无线视频 + 键盘 + 鼠标传输方案。

这个成本里还包含了一张 30 块左右的 USB WiFi 网卡。主要是我不太想让电脑自带 WiFi 一直被图传占着，毕竟没网还怎么 Web Coding……

由于我们比较穷，手里只有两套官方图传遥控器可以拿来做键鼠测试。不同车辆想测试键鼠时，经常要拆半天裁判系统，所以就想着自己做一套便宜一点、平时开发测试能直接用的图传键鼠模块。

作者本人之前也没做过这类无线图传 / 键鼠链路，预算又比较有限，所以第一版没有从零开始做硬件，而是直接买了现成的 MR300C 图传模块，在它的基础上做少量开发，先看看能不能达到一个比较满意的效果。

实际做完以后发现，视频效果并没有想象中那么好：实验室环境下 2 m、720P 只有十几帧，到了 5 m 还会继续往下掉。本来的目标其实是 1080P30……

不过键鼠控制链路的表现还算不错，实际接收频率大约能稳定在 400 Hz 左右，正常工作时控制手感和稳定性都比较能接受。

当然，如果单纯只想做无线键鼠，其实还能更便宜，两个 WiFi 模块基本就能解决。

所以最后还是决定把这套方案开源出来，给大家做个参考，也方便后面继续修改和扩展。

仓库里另外放了一份 AI_GUIDE.md，主要是为了让 AI 快速了解项目结构和几个关键接口，不需要每次都从头把所有源码读一遍，能少烧一点 token。

2. STM32 和通信协议

STM32 侧目前就三个文件：

stm32/
├── my_keyboard.c
├── my_keyboard.h
└── README.md

UART 收到的数据直接交给：

MyKeyboard_RxStream_Analysis(data, len);

内部会处理分包、粘包和重新同步。

例如：

void UART_RxCallback(uint8_t *data, uint8_t len)
{
    MyKeyboard_RxStream_Analysis(data, len);
}

主循环周期调用：

MyKeyboard_Failsafe_Update();
MyKeyboard_RxStat_Update();

分别用于断连保护和 Rx 频率统计。

解析后的鼠标数据：

MyKeyboard.Mouse.X
MyKeyboard.Mouse.Y
MyKeyboard.Mouse.Z

MyKeyboard.Mouse.Press_L
MyKeyboard.Mouse.Press_R
MyKeyboard.Mouse.Press_M

单个键盘按键可以直接这样读取：

MyKeyboard_Data[MY_KEY_W].Value
MyKeyboard_Data[MY_KEY_S].Value
MyKeyboard_Data[MY_KEY_A].Value
MyKeyboard_Data[MY_KEY_D].Value

目前提供的键位与规则保持一致：

W S A D
Shift Ctrl
Q E R F G
Z X C V B

链路状态：

MyKeyboard_Online
MyKeyboard_RxHz

其中：

MyKeyboard_Online
1 = 在线
0 = 离线

MyKeyboard_RxHz
每秒成功解析的有效控制包数量

超过 100 ms 没收到合法控制包时，Failsafe 会自动清空当前键鼠状态，避免断线之后还保持上一帧控制量。

PC → MCU 目前使用固定的 21 Byte 数据帧：


OffsetFieldType
0Headeruint8
1–4Mouse Xint32 LE
5–8Mouse Yint32 LE
9–12Mouse Zint32 LE
13Left Buttonuint8
14Right Buttonuint8
15–18Keyboard Valueuint32 LE
19Middle Buttonuint8
20CRC8uint8

帧头为 0x5C，小端序，最后一个 Byte 为 CRC。

Python 打包格式：

"<BiiiBBIB"

下面的数据都是我自己实际测出来的，只代表目前这套 MR300C、相机、网卡、固件和测试环境。

先说结论：没有达到 MR300C 标称的性能。

一开始我也怀疑过很多地方。

问商家为什么跑不到标称性能，商家让我买一个 720P30 的相机测试，说他们自己也是这么测的。

所以我又买了一款 720P30 UVC 相机做 A/B。

这款相机直连电脑时可以接近 30 FPS，但接到 MR300C 之后，表现跟原来的相机基本一样，还是上不去。

原来主要测试用的相机设置为：

1280 × 720 @ 60 FPS

一开始我怀疑是实验室 WiFi 环境太差。实验室设备很多，2.4G 基本所有信道都快爆了，所以后来干脆跑到排球场重新测。

结果确实比实验室好一点，但整体还是比较拉，所以至少可以排除“完全是实验室 WiFi 环境导致”的可能。

接收端网卡也换过：

PDD 30 块左右的 USB WiFi VS 笔记本自带 Intel BE200

实际大概只有 1–2 FPS 的差距。

BE200 连 MR300C 时链路速率能到大约 144 Mbps，如果这种情况下还是跑不起来，基本也可以排除 PC 接收端无线带宽不够。

也怀疑过 UVC 参数或者相机兼容性问题，所以去问商家测试时具体用了什么相机，但没有拿到具体型号，只告诉我随便买一个 720P30 的就行。

那这部分也没法继续复现他们的测试环境了，或许客服自己也不清楚。

电源也测过。直接用可调给 5V，限流设到 2A，实际整套大概也就吃 1A 左右，所以看起来也不是供电不足。

最后我能排查的基本都排查了，只能怀疑 MR300C 自己的视频处理 / 固件里可能存在某些限制。但因为没有源码，目前也没办法确认。

4. 控制链路和测试工具

虽然视频比较拉，但键鼠链路反而稳定得多。

实验室 2 m：

Test duration:      ≈20 min
PC Tx:              417.9 Hz
STM32 Rx:           417 Hz
>100 ms dropouts:   7

实验室 5 m：

Test duration:      ≈27 min
PC Tx:              416.5 Hz
STM32 Rx:           ≈420 Hz
>100 ms dropouts:   16

这里的 >100 ms dropouts 表示测试期间触发过多少次 100 ms Failsafe。

PC 和 STM32 的 Tx / Rx 统计窗口没有严格同步，所以有时候看到 RxHz 比 TxHz 高几 Hz 是正常的，不代表 STM32 收到了比 PC 发出去还多的数据。

正常连接时，控制数据基本能维持在：

≈410–420 Hz

目前实际用下来，MR300C 的视频对距离和 2.4G 环境比较敏感，但键鼠这种低数据量链路还是能保持比较高的接收频率。

仓库里顺便保留了开发过程中用到的两个视频测试脚本：

tools/
├── camera_direct_test.py
└── mjpeg_benchmark.py

camera_direct_test.py 用来直接测 UVC 相机接电脑时的分辨率、FOURCC、实时 FPS 和平均 FPS，主要用来先排除相机自己的问题。

电脑上有多个摄像头时可以修改：

CAMERA_INDEX = 1

mjpeg_benchmark.py 则直接读取：

http://10.10.10.1:8080

统计 MJPEG 流里的 JPEG 数量。

这个脚本不做 OpenCV 解码，也不开显示窗口，所以可以直接看 MR300C 实际送到电脑的帧率。

前面提到的有线 1280 × 720 ≈14.2 FPS 就是用这个测出来的。



5. 3D 打印外壳

机械顺手帮我画了一个 MR300C 的 3D 打印保护壳，STEP 文件已经一起放进仓库：

hardware/tuchuan3Dwaike.step

这个版本就是一个比较简单的保护壳，没有做得特别复杂。

上下都是镂空的，主要是考虑给 MR300C 留散热空间，所以它本身更偏向“保护外壳”，不是一个已经把上车安装方式全部设计好的成品结构。

如果需要装到车上，可以直接在这个 STEP 的基础上根据自己车上的安装位置再画几个螺丝孔、耳朵或者固定结构。

本来我是想让机械顺便把上车螺丝孔也一起画好的，但是懒狗机械天天就知道猛攻……所以最后先把这个保护壳版本放出来了。

不同车的安装位置本来也不一样，大家直接拿 STEP 按自己的车改反而更方便。
