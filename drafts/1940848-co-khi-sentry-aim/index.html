北京理工大学追梦战队哨兵自主导航

Nguồn: RoboMaster BBS · Tác giả: Dino.

Chuyên mục: Robot di động

这里开源的是我们在 RoboMaster 2026 赛季开发的一套 ROS 2 哨兵自主导航系统：

北京理工大学2026导航仓库

系统面向 RoboMaster 场地中的复杂地形、动态障碍、高速全向运动以及比赛自主决策，整体覆盖从双激光雷达、定位重定位、在线环境感知，到轨迹规划、MPC 跟踪和比赛行为树的完整链路。

在技术路线方面，我们的感知—规划—控制主线主要根据中科大 RoboWalker 2025 哨兵导航方案进行复现和工程化适配，并结合自身全向底盘、双雷达配置、ROS 2 系统以及比赛策略进行了较多修改。当前仓库中的主要模块包括 BehaviorTree.CPP、Point-LIO、GICP、ROGMap、MincoPlanner、SE(2) MPC，以及相关建图和标定工具。

1. 整体架构

整个工程大体可以分成三个部分：

  • 决策：BehaviorTree.CPP
  • 感知：双 Livox + Point-LIO + GICP + ROGMap
  • 导航：Nav2 + MincoPlanner + MPC

整体数据链可以简单理解为：

双 MID-360
    ↓
Livox Driver → Point-LIO → ROGMap → MincoPlanner → MPC → 底盘
                    ↑           ↑
                  GICP         Nav2
                    ↑           ↑
                预建地图    BehaviorTree

除此之外，还有两套比较重要的离线工具：

  • pcd_trans：预建地图处理；
  • dual_lidar_calibration：双雷达离线外参标定。[1]

2. 行为树：比赛战术与导航执行解耦

比赛决策使用 BehaviorTree.CPP v3 实现。

行为树通过 Blackboard 接收裁判系统状态、机器人自身状态、导航状态以及人工控制信息，再根据优先级选择当前行为，并向 Nav2 下发目标或者向通信模块发送姿态、资源请求等指令。

当前整个战术层可以抽象为三类全局模式：

  • Balance：均衡；
  • Offensive：进攻；
  • Defend：防守。

这些全局模式决定机器人当前更关注哪些比赛区域、使用哪组巡逻点以及在什么条件下前压、回防或补给，行为执行本身则继续拆分为导航、巡逻、姿态、资源、恢复等子逻辑，避免把所有比赛规则堆在一个大状态机里。

2.1 硬编码全局策略

从整体组织方式来看，我们的行为树和东大的方案有一些相似之处，都是通过比较清晰的优先级与抢占关系组织比赛行为。

比较明显的区别在于全局战术层，东大进一步使用 LLM 对比赛信息进行整合并参与全局策略生成。相比之下，我们当前的 Balance / Offensive / Defend 仍然主要依赖人工提前设计好的条件：

比赛时间、血量、弹量、前哨站状态、基地状态、人工指令等 → 条件判断 → 战术模式。

这种方式比较确定，也容易调试，但本质上还是把导航组和操作手赛前总结的比赛经验提前写进程序，对于复杂局势，不同条件之间的组合数量会快速增加，硬编码策略很难真正理解当前比赛上下文。

因此我们也认为，LLM 或其他更加智能的高层战术决策是目前系统比较明显的一块欠缺。

后续更希望形成这样的层级关系：

智能策略负责“想做什么” → Behavior Tree 负责“能不能做以及如何可靠执行” → Nav2 负责实际运动。

这样上层可以更加灵活，同时仍然保留行为树的确定性和安全边界。

2.2 Patrol List

比赛中的巡逻逻辑也没有和一组固定坐标完全绑定，我们把“现在应该巡逻”和“现在应该巡逻哪些点”拆开处理。不同战术模式可以切换对应的 PatrolList，例如防守模式使用己方区域巡逻点，Balance 使用中场巡逻点，Offensive 则切换到更加靠前的巡逻区域，这样赛中调整打法时，只需要切换 Patrol List，而不需要重新修改巡逻 Action 本身。

3. 坐标系与 GICP 重定位

我们默认将 map 固定在预建赛场地图原点 (0,0,0)，比赛中的巡逻点、战术区域、隧道、堡垒、补给区域、导航目标等语义坐标均人工定义在 map 下，Point-LIO 每次启动后则建立自己的 camera_init 世界坐标系，因此我们额外实现了一个 GICP Relocalization 功能包，通过预建 PCD 与 Point-LIO 在线输出的稠密点云进行配准，确定：map → camera_init变换。

当前 GICP 支持全局多初值搜索（几乎没用过）和人工 initial guess 两种初始化方式，并通过粗配准、精配准以及多个独立点云窗口的一致性确认最终定位结果，这样 Point-LIO 可以继续在自己的局部世界系中工作，而 Nav2、行为树和比赛语义始终使用固定 map

4. 双雷达与 Livox Driver

实车使用两台 Livox MID-360。

我们对 livox_ros_driver2 做了修改，同时支持：

  • 单雷达模式；
  • 双雷达模式。

双雷达情况下，没有再额外启动一个 ROS 点云融合节点，而是在 Driver 侧完成时间配对和外参变换后直接合并点云，后雷达通过标定得到的 back → front 外参转换到主雷达坐标系，然后组成统一点云交给 Point-LIO，这样做主要是希望融合尽可能靠近传感器原始时间戳，在高速平移或者小陀螺旋转时减少两帧点云时间差带来的误差。

Driver 与 Point-LIO 同时支持 Component 和 intra-process 通信，点云尽量通过指针移动方式传递，减少大点云在 ROS 2 中反复序列化和复制。当前仓库同时保留单、双 MID-360 两套启动配置。

5. 双雷达离线标定

仓库中提供了独立的 dual_lidar_calibration 功能包。

该模块可以直接读取 ROS 2 bag，根据双雷达点云和 IMU 数据进行离线外参标定，得到 Driver 使用的后雷达到前雷达变换。

相比单纯手工测量，我们希望实际标定结果能够直接进入驱动侧双雷达融合，同时保留点云对齐结果和统计信息用于人工检查。

因此雷达重新安装、机械位置发生变化后，可以重新采 bag 完成标定，而不需要依赖原有车辆的固定外参。

6. Point-LIO：面向高频状态和稠密点云的改造

Point-LIO 是整套系统的状态估计基础，但我们并没有完全按照原始数据链直接使用。

针对高速哨兵和 ROGMap 对完整环境点云的需求，我们主要做了以下修改。

稠密完整点云输出

定位使用的点云和建图使用的点云进行了分离。

ESIKF 可以继续使用降采样后的点完成快速状态更新，而 ROGMap 使用独立发布的：

/cloud_registered_full

获取更加完整的环境信息。

完整点云去畸变

对于稠密点云，我们根据点时间以及对应状态进行运动补偿，这部分主要针对小陀螺和高速运动状态下明显的点云拉伸问题。

Batch Update

定位更新按照较短时间窗口将点组织为 batch，再完成 iVox 查询和 ESIKF 更新。

这样可以减少过高频率的重复状态更新，同时仍保留高频位姿输出能力。

iVox 与计算量限制

我们同时调整了 iVox 更新范围、邻域查询和点云规模，避免高频完整点云直接导致地图查询量无限增加。

不同数据频率解耦

Point-LIO 的：

  • 状态更新；
  • odom；
  • 完整点云；
  • 可视化地图；

不再要求全部以相同频率发布。

实车目标是维持百 Hz 级状态输出和高频位姿更新，而完整点云根据 ROGMap 实际处理能力独立运行，避免大点云为了追随 odom 频率而制造额外计算和通信压力。

仓库当前配置中 odom、完整点云以及 ROGMap 消费链路也分别采用了针对实时性的 QoS 和队列策略。

7. ROGMap：在线三维环境感知

环境感知主要使用 ROGMap，我们保留了 ROG-Map 的滑动三维概率占据框架，并围绕地面哨兵进行了进一步适配，完整点云进入 ROGMap 后依次完成概率占据更新、动态遗忘和二维地形投影。

其中新增的 ProjectionLayer 根据单个 XY 栅格对应三维柱中的：

  • 占据数量；
  • 占据高度范围；
  • 高度跨度；
  • 垂直占据率；

将三维环境压缩为：

FREE / PASSABLE / OCCUPIED / UNKNOWN

四类二维语义。

在此基础上进一步生成 Signed ESDF，同时提供障碍外正距离、障碍内部负距离以及连续梯度查询，供：

  • 全局搜索；
  • MINCO；
  • Safety Checker；
  • Recovery；

共同使用。

另外加入了动态占据衰减、Dirty Column 更新以及进程内查询等工程机制，减少动态障碍残影和完整地图反复发布带来的开销。

8. MincoPlanner：从离散路径到连续轨迹

规划部分实现为 Nav2 Planner Plugin。

前端首先通过 A* / SMAC 得到离散路径，再进行：

局部截取 → ROGMap 边界裁剪 → Line-of-Sight 稀疏化 → 转角速度分配 → 时间初始化

最后交给 MINCO。

MINCO 同时优化中间控制点和各段持续时间，将普通离散 Path 转换为包含连续时间信息的轨迹。

当前主要考虑：

  • 平滑性；
  • ESDF 障碍距离；
  • 最大速度；
  • 最大加速度；
  • 原路径吸引；
  • 时间代价；

等因素。

同时支持两种导航模式：

PRIORMAP

使用预建 Nav2 地图提供全局拓扑搜索，ROGMap 主要负责局部在线安全约束。

这也是目前比赛使用的主要方式。

EXPLORATION

不依赖完整先验地图，在 ROGMap 当前有效区域内完成搜索和规划。

规划完成后还会执行独立 Safety Gate，对轨迹的速度、加速度、终点以及 ESDF 安全距离进行检查，避免单纯依赖优化器代价函数判断轨迹是否可执行，这部分仍存在执行问题尚未完项。

9. SE(2) MPC

Controller 使用针对全向底盘适配的 SE(2) 速度层 MPC。

状态为：

[x, y, yaw]

控制量为：

[vx, vy, wz]

MPC 直接使用 MINCO 输出的轨迹作为参考，并通过 qpOASES 求解约束 QP。

控制器内部还处理了：

  • 速度和角速度限制；
  • 加速度约束；
  • 控制延迟补偿；
  • 雷达与底盘中心杆臂补偿；
  • 速度死区；
  • Nav2 Speed Limit；
  • 小陀螺状态。

当前 Nav2 Controller Server 按 100 Hz 工作。

还有一个比较重要的约定：

Planner 和 Controller 使用的是全局世界坐标系平移速度。

也就是说，MPC 输出的 vx / vy 描述机器人在赛场世界系中的移动方向，而不是当前车头坐标系方向，底盘通信层再根据机器人当前 yaw，将世界系速度转换成实际底盘运动指令，因此即使机器人处于小陀螺状态，导航层仍然可以稳定描述“向赛场某个固定方向移动”，而不用随着车体朝向不断旋转速度参考。

10. 预建图工具

仓库中的 utils/pcd_trans 提供了一套用于比赛地图处理的工具。

主要包括：

  • 点云坐标变换；
  • 降采样；
  • 去噪；
  • AABB / ROI 裁剪；
  • 点云分类；
  • 地面、坡面和障碍处理；
  • PGM 地图生成；
  • YAML 生成；

11. 一些实时性上的工程处理

从实车调试来看，单个算法是否足够快并不是唯一问题，大点云、高频 odom 和多个 ROS 节点之间的数据传输同样容易成为瓶颈。

因此当前工程也做了一些比较偏系统层面的处理，包括：

  • Driver → Point-LIO intra-process，Point-LIO 完整点云指针移动发布；
  • 高频状态和大点云频率解耦；
  • odom 使用 latest-state 思路；
  • 地图进程内 Query Interface；
  • MINCO 固定局部规划范围和控制点规模；
  • MPC 凝聚 QP；
  • 各模块性能统计。

12. 方案对比与实现

这套系统并不是从零开始设计的一套全新导航框架。

我们这一赛季的感知—规划—控制主线，很大程度上是对中科大 2025 哨兵导航技术路线的复现、理解和实车工程化。

尤其是：

Point-LIO → ROGMap → 连续轨迹规划 → MPC

这条主线给了我们比较明确的系统方向。

在实际复现过程中，我们又结合自身条件加入了：

  • 双雷达 Driver 侧融合；
  • 双雷达离线标定；
  • Point-LIO 稠密去畸变链路；
  • GICP 上电重定位；
  • ROGMap 地面语义 Projection；
  • Nav2 PRIORMAP / EXPLORATION；
  • 世界系 SE(2) MPC；
  • 比赛 Behavior Tree；
  • Patrol List；
  • 离线 PCD / PGM 工具链。

而在决策层，我们和东大的思路存在比较明显的差距。

目前我们的行为树主要还是：

人工设计规则 + 人工设计优先级 + 人工设计战术切换。

东大进一步使用 LLM 整合比赛状态并参与全局战术决策，这一点在策略灵活性和上下文理解上比我们的硬编码方案更加智能。

这也是我们现在比较感兴趣、同时还没有真正解决的问题。

13. 目前还想继续做什么

虽然目前已经把整条系统链路跑通，但实际上还有不少问题没有做到我们希望的程度。

13.1 从软安全代价走向更强的硬约束

目前 MINCO 中的障碍避让主体仍然属于 ESDF 软代价，再配合优化完成后的离散 Safety Check，它可以拒绝危险轨迹，但并不能保证优化搜索过程始终位于安全可行空间。

后续希望进一步尝试：

  • ESDF Hard Constraint；
  • Safe Corridor；
  • 其他约束优化形式。

重点是研究如何在不过度限制 MINCO 优化自由度的同时，给轨迹提供更加明确的安全保证。

13.2 ROGMap 负障碍与更多地形

当前 Projection 对墙体、坡面、隧道等正向几何结构已经可以进行一定程度的区分，但地面机器人还有一个非常重要的问题：

没有障碍物，不代表那里可以走。

例如：

  • 高台边缘；
  • 断崖；
  • 无支撑区域；
  • 坡面终止区域；
  • 特殊高度突变。

这些负障碍很难直接通过普通 Occupancy 表达。

后续希望继续把地面支撑、先验高程、负障碍以及更多地形语义加入 ROGMap，使地图除了能够回答“这里有没有物体”，还能回答“这里的地面是否能够安全支撑机器人”。

13.3 动态障碍物分割

限于开发时间限制，当前对于动态机器人主要依赖 ROGMap 的概率占据和时间衰减，障碍离开后，旧占据会逐渐被清除。这种方式比较简单，但地图实际上并不知道：这个点属于静态墙体，还是另一台正在运动的机器人。

因此后续也希望尝试显式动态点云分割，将：

  • 静态环境；
  • 动态机器人；
  • 噪声与未知点；

进一步区分。

如果能够稳定得到动态目标的位置和速度，就有可能让 Planner 从目前的“看到障碍以后重新避障”进一步变成“考虑动态目标未来位置进行规划”。

13.4 面向更多车辆构型的运动学建模

现在 MincoPlanner 和 MPC 主要服务于我们的全向底盘。

对于全向底盘，二维位置轨迹和 [vx, vy, wz] 控制比较自然。

但换成：

  • 差速；
  • Ackermann；
  • 其他非完整约束底盘；

以后，一条几何上平滑的二维轨迹并不一定运动学可行。

因此后续也希望进一步研究在现有搜索 + MINCO 框架里加入不同车辆建模，使 Planner 本身能够考虑不同的车辆运动学。

13.5 更智能的比赛战术

现在复杂的比赛经验依然需要人工不断增加条件和优先级。

比赛状态越复杂，硬编码策略的维护成本也越高，因此我们也很想继续探索LLM / 高层智能策略 + Behavior Tree 确定性执行这样的组合。LLM 不直接控制机器人，而是根据比赛上下文生成受约束的战术意图；行为树继续负责合法性判断、优先级、安全条件和实际行为执行。

13.6 去NAV2框架

一开始的想法就是编写一套独立的导航框架，现有代码很大程度上已经不依赖于NAV2的各种组件，唯一用到的只有map server加载先验地图给A*提供静态搜索先验，各类话题数据均已经独立发布流转，由于本人较懒QAQ不想动了，所以代码启动页面和终端运行还包含着NAV2的很多组件输出。

14. 最后

这一赛季我们主要做的事情，其实就是不断把一个个单独能够运行的算法真正接到同一台哨兵上：

双雷达、Point-LIO、GICP、ROGMap、MINCO、MPC、BehaviorTree。

真正上车以后遇到的问题也远不只是算法公式本身，点云时间同步、去畸变、TF、地图坐标、动态障碍残影、轨迹安全、重规划跳变、控制延迟、世界系速度、小陀螺以及比赛战术之间都会互相影响，这次开源也没有想把它包装成一套已经完全解决问题的方案，更多是把我们目前做出来的实现、遇到的问题和还没有解决的方向放出来，和社区里做哨兵导航、行为决策和运动规划的大家一起交流。

如果大家也在折腾 ROGMap、MINCO、MPC、地形感知、动态障碍、LLM 战术或者其他哨兵导航方案，欢迎一起讨论，也欢迎 Issue 和 PR。
